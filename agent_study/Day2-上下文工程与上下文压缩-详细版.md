## 1. 为什么 Day2 是 Agent 工程核心

在真实系统里，很多 Agent 失败不是因为模型太弱，而是因为上下文工程不到位：

- 关键约束没注入：模型根本不知道“必须每天回酒店”。
- 关键信号被稀释：一堆无关对话覆盖了约束字段。
- 工具历史丢失：模型忘记“这个景点已经 geocode 失败过两次”。
- 压缩粗暴：把可执行证据压成空泛总结，导致下一轮重复试错。

一句话：

> 上下文工程决定 Agent 是否“可控”；上下文压缩决定 Agent 是否“可持续”。

## 2. 上下文工程的标准分层（面试可直接复述）

推荐你固定使用五层模型，回答统一且不漏项。

## 2.1 System Context（系统层）

定义：

- 长期稳定的行为边界与规则。

包括：

- 角色定义（你是旅行规划 Agent）
- 不可违反规则（格式、风控、隐私、禁止行为）
- 全局策略（先校验后交付）

在 `travel map` 映射：

- 生成结果必须结构化（如 `dailyPlans` / `validation`）。
- 不可臆造地理事实；不确定时需要显式标记。

## 2.2 Task Context（任务层）

定义：

- 本次任务的输入目标与硬约束。

包括：

- 用户需求
- 时间约束、预算约束、交通偏好
- 本轮成功定义（什么叫“规划完成”）

在 `travel map` 映射：

- `totalDays`、点位清单、点位类型、酒店锚点、城市范围。

## 2.3 Memory Context（记忆层）

定义：

- 跨轮或跨会话保留的偏好与经验。

包括：

- 用户偏好（亲子、慢节奏、低步行）
- 历史决策（上次删了哪个点，为什么）
- 稳定事实（该用户通常周末短途、偏好地铁）

在 `travel map` 映射：

- 用户默认偏好“少换酒店”和“每天不超过 8 小时活动”。

## 2.4 Tool Results Context（工具结果层）

定义：

- 外部工具产生的结构化事实证据。

包括：

- geocode 返回的经纬度/地址解析
- 路程时长
- 开放时间/天气（若接入）

在 `travel map` 映射：

- `place -> city_resolved` 对齐结果
- 段间 `duration_min` 的可信证据

## 2.5 Conversation Context（对话层）

定义：

- 用户与系统的自然语言交互历史。

用途：

- 保留语义连续性和临时指令。

风险：

- 容易膨胀且噪音高，必须压缩与裁剪。

## 3. 上下文装配原则：先结构化，再拼接

很多人会把所有文本直接拼进 prompt，这会导致不可控。更稳妥的流程是：

1. **结构化采集**：先把输入、约束、工具结果转成字段对象。  
2. **优先级排序**：硬约束 > 工具事实 > 偏好 > 对话风格。  
3. **预算分配**：按 token 预算给各层分配上限。  
4. **丢弃策略**：低优先级层先丢，不破坏可执行约束。  
5. **最终拼装**：只在最后一步拼给模型。

建议的优先级：

- P0：安全规则、硬约束、关键工具证据
- P1：本轮任务语义、近 1-2 轮操作记录
- P2：历史偏好、风格上下文
- P3：冗余礼貌对话

## 4. 上下文压缩：不是“做摘要”，是“保真压缩”

## 4.1 你要压的是什么

- 对话文本（高噪音）
- 工具调用轨迹（高价值，但体积大）
- 中间推理结果（有价值，但可能重复）

## 4.2 你不能丢的是什么

- 硬约束字段（天数、必回酒店、预算上限）
- 关键工具证据（失败原因、解析冲突）
- 当前计划状态（已完成步骤、剩余步骤）

## 4.3 推荐压缩策略（四段式）

1. **State Snapshot（状态快照）**  
   保留任务阶段、当前最佳方案、未解决问题。

2. **Constraint Ledger（约束台账）**  
   明确约束清单，逐条标记是否满足。

3. **Tool Evidence Digest（工具证据摘要）**  
   不是写成自然语言散文，而是字段化摘要（成功/失败次数、最新结果、可信度）。

4. **Decision Rationale（决策依据）**  
   保留关键“为什么”1-3 条，防止下一轮策略漂移。

## 5. 一个可执行的上下文模板（可直接用于工程）

你可以把上下文对象设计成如下结构（示意）：

```json
{
  "system_policy": {
    "must_return_structured_json": true,
    "safety_rules": ["no_fabrication", "constraint_first"]
  },
  "task": {
    "total_days": 2,
    "must_return_to_hotel": true,
    "places": [{"name": "故宫", "city_declared": "北京"}]
  },
  "memory": {
    "user_preferences": ["slow_pace", "family_friendly"]
  },
  "tool_evidence": {
    "geocode": [{"place": "故宫", "city_resolved": "北京市", "ok": true}],
    "travel_time": [{"from": "酒店", "to": "故宫", "duration_min": 25}]
  },
  "state": {
    "phase": "verify",
    "iteration": 2,
    "unresolved_issues": ["day_1_overloaded"]
  },
  "conversation_digest": "用户希望减少步行并保留核心景点"
}
```

重点：

- `task`、`tool_evidence`、`state` 必须结构化。
- `conversation_digest` 只保留最小语义摘要。

## 6. 在 travel map 里的落地映射（字段级）

## 6.1 输入到任务层

- `destinations`：国家/城市/点位层级
- `places`：景点与酒店（type = scenic/hotel）
- `totalDays`：用户期望天数
- `constraints`：必回酒店、步行/预算偏好（可扩展）

## 6.2 工具证据层

- geocode 结果：`query`、`resolved_city`、`resolved_country`、`confidence`
- route 结果：`from`、`to`、`duration_min`、`mode`、`timestamp`
- 错误证据：失败码、失败次数、最后失败原因

## 6.3 状态层

- `phase`: collect / plan / verify / repair / finalize
- `iteration`: 当前修复轮次
- `current_best_plan_id`: 当前最佳方案引用
- `issue_queue`: 待处理冲突（超时、跨城冲突、闭馆风险）

## 6.4 压缩后的输出层

- `plan_summary`
- `constraint_checklist`
- `key_tool_evidence`
- `delta_from_last_round`

## 7. 你最容易被追问的 6 个面试问题（附答题模板）

## Q1：上下文结构是不是就是 System Prompt + 对话历史？

标准回答：

> 不够。完整工程结构至少要分 System、Task、Memory、Tool Results、Conversation 五层。  
> 如果只给 system+history，会丢硬约束和工具证据，导致决策不稳定。

## Q2：上下文超长怎么办？

标准回答：

> 先做分层预算，再按优先级裁剪：硬约束和工具证据永远保留，对话先压缩。  
> 我会保留“状态快照 + 约束台账 + 工具证据摘要 + 关键决策依据”四段核心信息。

## Q3：压缩后丢了工具调用历史，模型重复调工具怎么办？

标准回答：

> 需要保留工具证据索引，不是保留全文日志。  
> 比如对每个地点维护 `success/fail_count`、`last_result_hash`、`last_error`，模型就能知道哪些调用已尝试过。

## Q4：RAG、Memory、Tool Results 怎么区分？

标准回答：

> RAG 是外部知识检索结果，Memory 是用户与任务历史偏好，Tool Results 是本任务中的事实执行结果。  
> 三者来源不同、时效不同、可信度评估方式也不同。

## Q5：为什么上下文工程有研究价值，不就是“拼 prompt”吗？

标准回答：

> 工业里主要难点是可控性和稳定性。  
> 上下文工程决定了约束是否被执行、错误是否可修复、成本是否可控，这些都直接影响线上成功率。

## Q6：如何证明你的上下文策略有效？

标准回答：

> 用固定评测集做 AB：比较成功率、违例率、平均工具调用次数、平均 token 成本、P95 时延。  
> 若压缩后成功率不降且成本下降，说明策略有效。

## 10. 常见漏洞与修复建议（Day2 专项）

- 漏洞 1：只保留对话摘要，不保留工具证据  
  修复：为每类工具维护证据索引（结果摘要 + 状态计数 + 最后错误）。

- 漏洞 2：把所有信息都当高优先级  
  修复：必须分层分级，不然压缩时无法决策。

- 漏洞 3：压缩后缺失约束台账  
  修复：硬约束单独维护 checklist，不走自然语言摘要。

- 漏洞 4：没有状态快照，导致阶段漂移  
  修复：每轮保留 `phase`、`iteration`、`unresolved_issues`。

- 漏洞 5：没有压缩效果评估  
  修复：最少比较三项指标：成功率、成本、时延。

## 11. 今日结论（可复述版）

1. 上下文工程是 Agent 可控性的底座，不是“附属 prompt 技巧”。  
2. 高质量上下文必须分层、结构化、可压缩、可追踪。  
3. 压缩的目标是保真传递关键决策信息，而不是把文本变短。  
4. 在 `travel map` 场景中，最关键的是保留约束台账和工具证据索引。  
5. 只要你能讲清“五层结构 + 压缩策略 + 指标验证”，Day2 就达到中高级工程面试标准。
