# Day 6 学习文档：评测体系与线上治理（详细版）

文档版本：v1.0  
日期：2026-08-06  
适用对象：已完成 Day1-Day5，需要把 Agent 从“能跑”推进到“可上线可优化”的开发者  
项目绑定：`map`（travel map / travel planner agent）

---

## 0. 今天目标

1. 能建立 Agent 评测指标体系（离线 + 线上）。
2. 能设计回归集、对照组与 AB 评测流程。
3. 能搭建基本线上治理机制（监控、告警、回放、降级）。
4. 能回答“怎么证明你优化真的有效”。
5. 让 `travel map` 拥有可迭代优化闭环。

---

## 1. 为什么 Day6 决定你是否像“工程师”

没有评测与治理：

- 你不知道优化是进步还是退步
- 线上问题不可见，靠用户投诉
- 改一次 prompt 就可能引入回归

有评测与治理：

- 每次改动都有客观证据
- 问题可监控、可定位、可回放
- 团队能稳定迭代，不靠运气

## 2. 指标体系（建议最小集合）

## 2.1 效果指标（Quality）

- 任务成功率（可执行计划比例）
- 约束违例率（天数超载/跨城冲突/闭环失败）
- 修复成功率（首次失败后可收敛比例）
- 个性化匹配率（符合用户偏好程度）

## 2.2 效率指标（Efficiency）

- 平均工具调用次数
- 平均修复轮次
- token 使用量
- 外部 API 成本

## 2.3 性能指标（Performance）

- 平均响应时延
- P95/P99 时延
- 超时率

## 2.4 稳定性指标（Reliability）

- 错误率
- fallback 触发率
- 线上重试率

---

## 3. 离线评测设计（必须会）

## 3.1 评测集构建

至少覆盖：

- 单城简单案例
- 多城复杂案例
- 天数不足冲突案例
- 工具失败/数据缺失案例

建议：

- Day6 先做 20-50 条小集
- 每条都有期望约束（不是唯一答案）

## 3.2 评测方式

- 规则评测：约束是否满足
- 模型评测：答案可读性与解释性（可选）
- 人工抽检：高风险样本复核

## 3.3 对照实验

- Baseline：无修复闭环
- Candidate：有修复闭环
- 对比指标：成功率、成本、时延

---

## 4. 线上治理框架

## 4.1 监控

监控项：

- 请求量、成功率、错误率
- 工具调用失败率
- 平均轮次、平均 token 成本

## 4.2 告警

建议阈值：

- 成功率下降超过 X%
- P95 时延飙升超过 Y%
- 某工具失败率连续超阈值

## 4.3 回放（Replay）

必须可回放：

- 输入上下文快照
- 工具调用轨迹
- 校验与修复过程
- 最终输出与错误

## 4.4 降级

降级顺序示例：

- 关闭高成本非关键工具
- 限制修复轮次
- 返回保底方案 + 风险提示

---

## 5. travel map 的评测与治理落地建议

## 5.1 离线集维度

- 城市数量（1/2/3）
- 点位数量（3/6/10）
- 用户天数（充足/不足）
- 是否酒店锚点（有/无）
- 是否跨城（是/否）

## 5.2 关键指标优先级

优先看：

1. 约束违例率
2. 修复成功率
3. 平均调用成本
4. P95 时延

## 5.3 每次迭代必须交付的评测报告

- 变更说明
- 评测集结果对比（前后）
- 失败案例 TopN
- 是否允许上线

## 6. Day6 面试问答模板

## Q1：你怎么评估 Agent，不会只看主观好不好看吧？

答：

> 我分四类指标：效果、效率、性能、稳定性。  
> 对规划类任务最关键是约束违例率和修复成功率，而不是文案好看程度。

## Q2：如何防止优化后回归？

答：

> 建固定离线回归集，每次变更都跑；关键指标达阈值才上线。  
> 线上再用灰度和告警兜底。

## Q3：线上出问题怎么定位？

答：

> 依赖可回放 trace：看输入快照、工具轨迹、校验修复链路。  
> 没有 trace 的系统无法快速定位根因。

## Q4：成本太高怎么办？

答：

> 做工具去重缓存、限制轮次、压缩上下文、关闭低收益工具。  
> 以“成功率损失最小化”为前提做成本优化。

## 9. 今日结论

1. 没有评测，Agent 优化就是玄学。  
2. 没有治理，Agent 上线就是风险。  
3. `travel map` 进入产品化阶段的关键不是再加功能，而是建立可量化迭代体系。
