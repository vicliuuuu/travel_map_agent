## 1. 先把三件事分开：RAG、Memory、Tool Results

## 1.1 RAG 是什么

- 来源：外部知识库
- 目的：补充事实知识
- 时效：随文档更新而更新
- 典型内容：景点规则、开放时间、签证与交通政策

## 1.2 Memory 是什么

- 来源：用户历史交互与系统决策沉淀
- 目的：个性化与连续性
- 时效：长期累积
- 典型内容：偏好慢节奏、亲子优先、预算敏感

## 1.3 Tool Results 是什么

- 来源：本轮工具执行证据
- 目的：支撑当前决策
- 时效：短期高价值
- 典型内容：当前 geocode 结果、当前路程时长

一句话区分：

> RAG 管“外部知识”，Memory 管“用户与历史”，Tool Results 管“当前事实”。

---

## 2. RAG 检索链路（工程全流程）

## 2.1 Query Rewrite（意图重写）

目标：

- 把用户自然语言改写成可检索表达。

示例：

- 原问题：“两天北京亲子游怎么安排？”
- 检索意图：`北京 亲子 景点 开放时间 交通耗时 周末拥挤`

## 2.2 Recall（召回）

可选策略：

- 稠密检索（向量）
- 稀疏检索（关键词/BM25）
- 混合检索（推荐）

## 2.3 Rerank（重排）

为什么必须单独做：

- 召回阶段强调“广”，重排阶段强调“准”。
- 不重排会把噪声文档注入模型，导致答非所问。

## 2.4 Grounding（证据注入）

原则：

- 只注入高相关片段
- 注入时保留来源标识
- 控制片段数量，避免稀释任务约束

## 3. Memory 系统设计（短期与长期）

## 3.1 短期记忆（Session Memory）

内容：

- 本轮目标变化
- 已执行动作
- 临时偏好（例如“今天只想轻松路线”）

更新策略：

- 每轮更新
- 会话结束可丢弃或摘要归档

## 3.2 长期记忆（User Memory）

内容：

- 稳定偏好（慢节奏、亲子、餐饮禁忌）
- 历史决策经验（曾拒绝高强度路线）

更新策略：

- 仅在高置信事件写入
- 支持冲突检测与版本管理

---

## 4. Memory 写入策略（防污染）

建议准则：

- 只写入“被重复验证的偏好”
- 一次性情绪表达不直接固化
- 可撤销、可过期、可追溯

冲突处理：

- 新记忆与旧记忆冲突时，提升“新近度权重”
- 同时保留冲突证据，避免硬覆盖

## 5. travel map 场景的 RAG + Memory 融合

## 5.1 RAG 在项目中的位置

- 规划前：检索目标城市景点规则与开放时间
- 校验前：检索季节性风险（高温/暴雨）
- 交付时：给出依据引用

## 5.2 Memory 在项目中的位置

- 规划阶段注入长期偏好（例如“每日不超 8 小时”）
- 修复阶段作为动作优先级依据（先删不感兴趣点）
- 输出阶段体现“为什么这么排”

## 5.3 一个组合示例

- RAG 告诉你“某景点周一闭馆”
- Tool 告诉你“跨城段 150 分钟”
- Memory 告诉你“用户不接受高强度”
- Agent 决策：换日 + 删低优先级远点 + 提供替代点

## 6. 面试高频问答模板（Day5）

## Q1：为什么 RAG 不等于 Memory？

答：

> RAG 面向外部知识事实，Memory 面向用户历史偏好。  
> 两者来源和更新机制都不同，混在一起会造成污染和误导。

## Q2：为什么要 rerank？

答：

> 召回只保证“可能相关”，不保证“最相关”。  
> rerank 是把高价值证据放到前面，减少模型被噪声误导。

## Q3：Memory 为什么不能每轮都写？

答：

> 每轮写会把临时噪声固化成长期偏好。  
> 应该按置信度和重复出现次数写入，避免记忆污染。

## Q4：RAG 注入越多越好吗？

答：

> 不好。注入过多会稀释任务约束并增加 token 成本。  
> 应做“少量高相关 + 可追溯来源”的精注入。

## Q5：如何评估 RAG/Memory 是否有效？

答：

> 看事实错误率、个性化匹配率、用户二次修改率、token 成本与时延变化。

## 9. 今日结论

1. RAG 负责外部知识，Memory 负责个性连续，Tool 负责当前事实。  
2. 三者同时存在时，Agent 才能“知事实、懂用户、会执行”。  
3. `travel map` 的下一步竞争力来自“知识 + 偏好 + 证据”融合治理。
