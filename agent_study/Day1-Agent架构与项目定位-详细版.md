## 1. 先统一认知：什么是 Agent

### 1.1 标准定义（工程视角）

Agent 是一个以目标达成为导向的系统，具备：

- 任务理解与拆解能力（Goal + Planning）
- 外部工具调用能力（Tool Use）
- 状态跟踪与记忆能力（State + Memory）
- 结果校验与修复能力（Verify + Repair）
- 可观测与评估能力（Trace + Eval）

一句话：

> Agent = LLM（推理）+ 工具（行动）+ 状态机（流程）+ 校验修复（可靠性）

### 1.2 常见误区（面试高频）

- 误区 1：Agent = Prompt Engineering  
  实际：Prompt 只是入口，Agent 核心是多步执行与闭环修复。

- 误区 2：Agent 一定要训练  
  实际：大量高价值 Agent 工作是 train-free（流程、工具、校验、评测）。

- 误区 3：调用 API 就算 Agent  
  实际：一次性 API 编排不等于 Agent，必须有任务状态与反馈闭环。

### 1.3 Chatbot / RAG / Agent 快速区分（你必须讲得清）

这一段是 Day 1 的关键补丁。很多面试追问并不是问“你会不会做”，而是先看你有没有边界意识。

先用一句话区分：

- **Chatbot**：主要是“对话生成”，重点在表达与交互。
- **RAG**：主要是“先检索外部知识再生成”，重点在事实依据。
- **Agent**：主要是“为目标进行多步行动并闭环修复”，重点在任务完成。

再用“输入-过程-输出”区分：

- **Chatbot**
  - 输入：用户问题
  - 过程：模型直接生成回复（可能少量上下文拼接）
  - 输出：一段回答文本
  - 典型风险：说得通顺但不一定可执行

- **RAG**
  - 输入：用户问题 + 知识库
  - 过程：检索（召回）-> 可能重排（rerank）-> 生成
  - 输出：带外部依据的回答
  - 典型风险：召回不准导致“有依据但答错”

- **Agent**
  - 输入：目标 + 约束 + 可用工具
  - 过程：规划 -> 调工具 -> 观察 -> 校验 -> 修复 -> 交付
  - 输出：可执行结果（不仅是文字），并包含过程证据
  - 典型风险：流程失控（死循环、工具误调、成本过高）

用你的 `travel map` 项目做一眼能懂的例子：

- **如果是 Chatbot 版本**  
  用户说“帮我规划北京两日游”，系统直接给一段建议文本，不查真实路程，不验证是否走得完。

- **如果是 RAG 版本**  
  系统先查“北京景点介绍/开放时间/旅游攻略文档”，再生成建议，事实更丰富，但仍不一定做真实路程约束求解。

- **如果是 Agent 版本（你当前方向）**  
  系统会调用地图工具拿真实地理与路程，生成 `dailyPlans`，并对“天数可行性、城市归属、酒店闭环”做校验，失败后触发重排。

面试可直接背的短答案（20 秒）：

> Chatbot 解决“怎么说”，RAG 解决“基于什么事实说”，Agent 解决“如何把目标真正做成”。  
> 三者不是互斥关系，RAG 常是 Agent 的一个模块，而不是替代 Agent。

## 2. Agent 核心架构（面试可直接回答）

建议按“八层”回答，兼顾完整性和工程落地。

## 2.1 Goal 层（目标层）

- 输入用户目标与约束（预算、时间、偏好、风格）。
- 将自然语言目标转为结构化任务对象。
- 输出任务契约（task contract）。

在 `map` 项目中的映射：

- 输入：目的地、景点、天数、酒店锚点、偏好。
- 输出：可规划任务对象（destinations + places + constraints）。

## 2.2 Planning 层（规划层）

- 任务分解：全局目标 -> 子目标 -> 执行步骤。
- 确定步骤依赖和终止条件（何时算完成/失败）。

在 `map` 项目中的映射：

- 先分天，再排序，再填交通段。
- 若不可行，进入修复流程而不是直接结束。

## 2.3 Memory 层（记忆层）

- 短期记忆：当前会话与工具调用历史。
- 长期记忆：用户偏好和历史决策（例如“少换酒店”）。

在 `map` 项目中的映射：

- 短期：本轮 geocode 和路线查询结果。
- 长期：用户长期偏好（亲子、慢节奏、少步行）。

## 2.4 Tool 层（工具层）

- 调用外部事实源：地图、天气、营业时间、知识库。
- 提供工具 schema、参数校验、错误码标准化。

在 `map` 项目中的映射：

- geocode 工具、travel time 工具、可扩展天气与开闭馆工具。

## 2.5 Execution 层（执行层）

- 将计划转为可执行动作，按步骤触发工具。
- 记录每一步行动结果（用于回放与审计）。

在 `map` 项目中的映射：

- 形成 `recommendedOrder`、`dailyPlans`、`roadbook`。

## 2.6 Verification 层（校验层）

- 验证输出与约束一致性（时间、预算、地理逻辑）。
- 给出机器可判定结果（pass/fail + reason）。

在 `map` 项目中的映射：

- 天数可行性、地理归属一致性、酒店闭环一致性。

## 2.7 Repair 层（修复层）

- 当校验失败时自动修复（删点、拆天、换序、替代点）。
- 重试并收敛，避免“报错即结束”。

在 `map` 项目中的映射：

- 2 天放不下 6 个远距景点时，自动裁剪或拆分方案。

## 2.8 Observability & Eval 层（可观测与评估）

- 全链路 trace（每轮 thought/action/observation 摘要）。
- 指标：成功率、违例率、重试轮次、延迟、成本。

在 `map` 项目中的映射：

- 对固定测试集跑回归，比较优化前后可行率。

## 3. 两种主流 Agent 范式：ReAct vs Plan-and-Execute

## 3.1 ReAct（边想边做）

流程：

1. Thought（当前推理）
2. Act（调用工具）
3. Observation（拿到结果）
4. 循环直到完成

优点：

- 灵活，适应动态环境。
- 对信息不全任务更有效。

缺点：

- 容易死循环。
- 成本不可控（调用次数多）。

适用：

- 信息探索型、查询型任务。

## 3.2 Plan-and-Execute（先计划再执行）

流程：

1. 先生成全局计划
2. 再按计划执行步骤
3. 必要时局部重规划

优点：

- 结构清晰，可控性高。
- 便于约束注入与审计。

缺点：

- 初始计划错误时可能全局偏航。

适用：

- 约束明确、流程可预定义的任务。

## 3.3 你的项目建议

`map` 项目优先使用“Plan-and-Execute + 局部 ReAct 修复”的混合策略：

- 主流程走计划式（稳定、便于评估）。
- 修复阶段走 ReAct（灵活应对异常）。

## 4. 你的 travel map 项目：从功能到 Agent 的完整映射

## 4.1 当前可视为“已具备”的能力

- 有目标输入结构（地点、天数、点位类型）。
- 有工具调用能力（地理编码/路程）。
- 有结构化输出（dailyPlans、validation 等）。
- 有基础可行性判定。

## 4.2 当前“未完全闭环”的关键缺口

- 缺少显式状态机（各阶段边界不清）。
- 缺少统一 repair 策略（失败后多为提示，不一定自动收敛）。
- 缺少稳定评测集与指标看板（优化效果难量化）。
- 缺少长期记忆注入（用户偏好跨会话复用不足）。

## 4.3 Day 1 视角下的目标定位句（建议背诵）

> 我们当前项目已经是工具增强型 Agent 雏形，但下一步核心是补齐状态机、校验修复闭环和评测体系，让系统从“单轮规划器”升级为“可收敛的任务 Agent”。

## 5. 面试问答模板（第 1 天必须掌握）

## Q1：Agent 核心架构是怎样的？

参考回答：

> 我按八层实现：目标层、规划层、记忆层、工具层、执行层、校验层、修复层、评估层。  
> 在我的 travel map 项目中，目标是多约束旅行规划，工具层接地图事实，校验层判定天数与地理可行性，修复层负责自动重排并输出可执行方案。

## Q2：为什么不用“直接调用 Claude Code 或公司内部 Agent”？

参考回答：

> 通用 Agent 强在广覆盖，但业务约束和输出契约不一定贴合。  
> 我们需要可控 schema、可解释校验、稳定回归评测，这要求做领域化编排，而不是只依赖通用对话能力。

## Q3：为什么要引入状态机，会不会过度设计？

参考回答：

> 只要任务涉及多轮工具调用与失败重试，状态机不是过度设计，而是必要的可靠性基础。  
> 没有状态机就难以定义终止条件、重试上限和可观测日志。

## Q4：RAG 和 Agent 的关系是什么？

参考回答：

> RAG 是 Agent 的知识增强模块，不是 Agent 的全部。  
> Agent 解决“怎么做任务”，RAG 解决“回答基于哪些外部事实”。

## Q5：你这个项目的研究价值在哪，不训练是不是价值低？

参考回答：

> 研究价值在系统层：约束满足、工具编排、失败修复、评测治理。  
> 这些是工业可落地的关键瓶颈，通常先于模型训练发生，且收益更直接。

## Q6：如何防止 Agent 死循环？

参考回答：

> 三层防护：  
> 1) 轮次上限（max iterations）  
> 2) 改善阈值（若连续无收益则停止）  
> 3) 失败分类回退（无法修复时输出保底方案）

## 8. 常见漏洞与修正建议（避免面试翻车）

- 漏洞 1：只讲模型，不讲系统  
  修正：必须补充流程编排、工具接口、异常恢复和评测。

- 漏洞 2：只讲 happy path，不讲失败策略  
  修正：每个关键步骤都要有 fallback 设计。

- 漏洞 3：概念堆砌，没有项目映射  
  修正：每个术语都用 `travel map` 举 1 个具体例子。

- 漏洞 4：没有量化指标  
  修正：至少准备 3 个指标和 1 次前后对比。

- 漏洞 5：把 RAG、Memory、Tool Result 混为一谈  
  修正：明确三者定义与注入时机不同。

## 9. 今日学习结论（可复述版）

1. Agent 的本质是“目标驱动的多步闭环执行系统”，不是“会回答问题的模型”。  
2. 真正工程价值在于：工具调用、约束校验、自动修复、评测治理。  
3. `travel map` 已具备 Agent 雏形，下一步应补状态机、repair 闭环和评测体系。  
4. 只要你能把“架构-流程-指标-案例”讲通，就已达到中高级面试的核心要求。
