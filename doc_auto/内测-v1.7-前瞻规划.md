# 内测 v1.7 前瞻规划：可观测与评测体系

> 创建日期：2026-08-06
> 状态：**仅规划，尚未开发**
> 基线版本：[`内测-v1.6-前瞻规划.md`](./内测-v1.6-前瞻规划.md)
> 终态参照：[`map-travel-agent-终极构想.md`](./map-travel-agent-终极构想.md)

本版本把从 v1.3 起持续埋点的 trace 数据，收口为**可观测与评测体系**：全链路 trace 查看、指标看板、固定评测集回归、回放复盘。让"优化有没有效果"从主观变成可量化。

> 注意：本版本不是"新埋点"，而是"消费 v1.3–v1.6 已埋的点"。前置版本埋点是否规范，直接决定本版本能否落地。

---

## 1. 版本定位

| 维度 | v1.6（前置） | v1.7（本版本） |
|------|-------------|----------------|
| 可观测 | 有 trace 数据，无统一查看 | trace 查看 + 指标看板 |
| 评测 | 分散回归样例 | 统一评测集 + 自动化回归 + 前后对比 |
| 复盘 | 无 | 单次请求可回放"为什么改了路线" |

一句话目标：**建立"看得见、量得准、可复盘"的治理能力，为持续迭代提供数据依据。**

---

## 2. 前瞻规划

### 2.1 P0（必须）

1. **Trace 查询与可视化**
   - 统一 trace 存储（内测本地库/文件，结构见 v1.3 §4）；
   - 提供查询：按 requestId / traceId 拉取完整链路（状态流转、工具、校验、修复、记忆事件）；
   - 内测调试面板：时间线视图展示每轮 thought/action/observation 摘要与修复 diff。

2. **核心指标看板**
   - 指标采集器聚合 trace，产出：成功率、违例率、平均重试轮次、平均延迟、外部调用成本、兜底触发率、缓存命中率、局部重算复用率；
   - 支持按时间窗与版本对比。

3. **评测集与自动化回归**
   - 沉淀标准评测集（跨国跨城、同城高密、无酒店、超载、闭馆冲突、换酒店等场景，覆盖 v1.3–v1.6 能力）；
   - 每次改动跑评测集，输出与上一基线的指标对比报告；
   - 评测结果纳入版本准入判定。

### 2.2 P1（应做）

1. **回放复盘**
   - 对任一历史请求，重放其决策链路，展示"为什么是这个顺序、为什么删了某点、修复了几轮"。

2. **告警阈值**
   - 关键指标超阈值（如兜底率突增、成功率下降）时在看板高亮/告警。

3. **生产级限流与滥用防护**（从 v1.2 顺延而来）
   - v1.2 仅实现「单机内存限流」，重启/多实例即失效，且无滥用防护；
   - 本版本升级为可持久化/可跨实例的限流（如基于存储或网关层），并接入 §2.1 的指标看板与告警（异常流量、单 IP 突增、成本飙升）；
   - 与可观测体系统一：限流触发、拒绝率、Top 调用方等纳入指标与 trace。

### 2.3 P2（可选）

1. **A/B 对比评测**
   - 同一评测集下对比两套策略/参数的指标差异，辅助策略调优。

## 3. 关键方案设计

### 3.1 指标体系

| 类别 | 指标 | 来源事件（v1.3+ 埋点） |
|------|------|------------------------|
| 效果 | 规划成功率、收敛成功率 | `validation`、`state_exit` |
| 质量 | 违例率、平均总时长/换乘 | `validation`、`scoring` |
| 修复 | 平均修复轮次、兜底率 | `repair_action`、`fallback` |
| 性能 | 端到端延迟、各阶段耗时 | `state_enter/exit`、`tool_call` |
| 成本 | 外部调用数、缓存命中率 | `tool_call` |
| 增量 | 局部重算复用率 | `incremental_replan` |
| 记忆 | 偏好命中/注入生效率 | `memory_read`、`preference_inject` |

### 3.2 评测流程

```
for case in eval_set:
    trace = run_plan(case)
    metrics = extract_metrics(trace)
    record(case, metrics)
report = compare(current_metrics, baseline_metrics)
gate = all(pass_thresholds(report))   # 准入判定
```

## 4. 埋点设计（本版本以"消费+补全"为主）

### 4.1 埋点补全项

| 事件点 | eventType | 补全 payload | 用途 |
|--------|-----------|--------------|------|
| 请求总览 | `request_summary` | `totalDurationMs`、`finalStatus`、`repairRounds`、`tokenCost` | 请求级汇总 |
| 评测运行 | `eval_run` | `caseId`、`metrics`、`baselineDiff` | 回归对比 |
| 指标快照 | `metric_snapshot` | `window`、`aggregatedMetrics` | 看板时序 |

### 4.2 埋点治理要求

- 校验 v1.3–v1.6 埋点字段齐全（缺字段的版本需回补，否则指标不可算）；
- trace 存储需支持按 requestId 精确检索与批量导出；
- 指标计算逻辑与埋点字段解耦，字段变更需版本化。

## 5. 评价指标（验收标准，"评测体系自身"的验收）

### 5.1 功能性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| trace 可检索率 | 任一请求可按 requestId 查到完整链路 | 100% |
| 指标可算率 | 定义的核心指标均能从 trace 稳定计算 | 100% |
| 评测集自动化率 | 评测集可一键跑完并出对比报告 | 100% |
| 回放还原率 | 回放能还原原始决策关键节点 | ≥ 95% |

### 5.2 准入门禁能力

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 门禁有效性 | 指标不达标时准入判定能正确拦截 | 100% |
| 基线对比正确率 | 与历史基线对比数值正确 | 100% |

### 5.3 性能指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 评测集运行时长 | 全量评测集跑完时长 | 可接受（≤ 约定上限） |
| 埋点开销占比 | 埋点对端到端延迟的额外开销 | ≤ 5% |

### 5.4 验收结论判定

- **通过**：5.1 全达标，5.2 全达标，5.3 达标；且能对 v1.3–v1.6 历史请求成功产出指标报告；
- **不通过**：trace 可检索率或指标可算率不达标必须回炉（通常意味着前置版本埋点缺失，需回补）。

## 7. 风险与边界

1. 若前置版本埋点不规范，本版本无法计算指标——因此各版本埋点验收是硬前提；
2. 评测集需持续维护，避免过拟合固定样例；
3. 指标口径变更需版本化，避免历史对比失真；
4. 内测存储方案需评估数据量增长与清理策略。

## 8. 关键任务拆解（难点分解）

> 本版本最硬的是"回放复盘"（要能重现决策）与"指标计算口径"（错了会误导迭代）。

### 8.1 难点：Trace 存储与检索

**子步骤**
1. 选型：内测用轻量方案（JSONL 落盘 / SQLite），键为 `requestId`，值为该请求全部 trace 事件。
2. 写入：v1.3 `tracer` 的缓冲批量刷盘，保证不阻塞主流程。
3. 检索 API：`GET /api/trace/:requestId` 返回按 ts 排序的事件序列。
4. 导出：支持批量导出评测集所有请求的 trace（供离线分析）。

**完成判据**：任一请求可按 requestId 查到完整链路 100%。

### 8.2 难点：指标计算口径（错了会误导所有迭代决策）

**子步骤**
1. 为每个指标写"计算函数 + 依赖事件 + 口径说明"三件套（如"成功率 = finalStatus=ok 的请求数 / 总请求数"）。
2. 事件字段校验：跑一遍 v1.3–v1.6 历史 trace，检查计算所需字段是否齐全，缺失项回填到对应版本埋点（硬前提）。
3. 指标计算与埋点解耦：字段变更走 `schemaVersion`，历史数据按版本兼容解析。
4. 单测：构造已知 trace，断言指标计算结果精确匹配。

**关键实现点**：口径必须书面固化并版本化，避免"同名指标不同算法"导致历史对比失真。

**完成判据**：核心指标可算率 100%，指标单测通过，与历史对比数值正确。

### 8.3 难点：回放复盘（重现"为什么这么决策"）

**子步骤**
1. 时间线重建：按 trace 事件序列还原 状态流转 → 工具结果 → 校验结论 → 修复 diff。
2. 决策注解：对每个 `repair_action` 展示 `reason/beforeScore/afterScore/diff`；对最终顺序展示 v1.4 打分构成。
3. 可视化：内测调试面板以时间线 + 折叠详情呈现（不追求生产级 UI）。
4. 还原度校验：对同一请求，回放展示的关键节点应与原始 trace 一一对应。

**关键实现点**：回放是"读 trace 重现"，不是"重跑规划"——避免因外部数据变化导致复盘失真。

**完成判据**：回放还原率 ≥ 95%。

### 8.4 难点：评测集与准入门禁

**子步骤**
1. 冻结评测集：覆盖 v1.3–v1.6 各能力场景，每个 case 标注期望（可行/需修复/应兜底）。
2. 一键运行器：批量跑 → 抽取指标 → 与 baseline 对比 → 出报告。
3. 门禁规则：定义各指标阈值，任一 P0 指标回退即判定不通过（可拦截）。
4. baseline 管理：每次通过后可将当前指标固化为新 baseline。

**完成判据**：评测集自动化率 100%，门禁能正确拦截不达标改动。

## 9. 建议实施顺序（本版本内）

1. 先做 8.1 存储检索 + 8.2 校验历史埋点完整性（若发现前置版本缺字段，先回填）；
2. 再做指标计算 + 8.4 评测门禁（让迭代有量化依据）；
3. 最后做 8.3 回放复盘（锦上添花但对定位问题极有价值）。
