# 内测 v1.1 改进规划（草案）

> 创建日期：2026-07-31  
> 状态：**仅规划，尚未开发**  
> 基线版本：[`内测-v1.0.md`](./内测-v1.0.md)

本文档记录内测 v1.0 之后拟优先解决的问题与新功能方向，供下一版本设计与评审使用。**当前代码不做任何改动。**

---

## 1. 背景：内测 v1.0 暴露的核心问题

### 1.1 现象：模型幻觉仍然严重

在实际使用中，LLM 会生成**看似合理但事实错误**的内容，例如：

| 类型 | 示例 | 危害 |
|------|------|------|
| 张冠李戴 | 「北师大中的鲁迅故居」 | 鲁迅故居实际在北京阜成门内，与北师大无关 |
| 虚构可行性 | 「可以提前预约参观北理工的实验室」 | 高校实验室通常不对游客开放，不可作为行程建议 |
| 泛化过度 | 把普通地标描述成有特殊参观渠道 | 用户按路书执行时会落空 |

**根因分析（初步）：**

1. **提示词当前侧重「输出结构」**，对事实准确性约束不足；
2. **缺少事实校验环节**，模型未被要求区分「确定事实 / 合理推断 / 不确定」；
3. **工具链只覆盖地理编码与车程**，未验证「景点是否真实存在、是否位于目标城市、是否对游客开放」；
4. **单次生成即交付**，没有「生成 → 反思 → 修正」的闭环。

内测 v1.0 的 Agent 流程是：工具调用 → 直接输出 JSON 路书。这对「顺序 + 路程」有帮助，但**不能防止常识性胡说**。

---

## 2. 期望新功能：用户输入甄别

决策层仍是 LLM，但需要在规划前/规划中增加**输入合理性审查**，至少覆盖以下两类。

### 2.1 情形一：时间不支持游览全部景点

**场景示例：**

> 用户在北京，计划 **1 天** 内游览：故宫、长城、什刹海、天坛、地坛、恭王府。

这在现实中几乎不可能完成（路程 + 排队 + 游览时长均超标）。

**期望行为：**

1. **识别超载**：根据景点数量、典型游览时长、景点间通勤（Google Maps 工具），判断「在给定天数内是否可行」；
2. **给出明确反馈**：告知用户当前组合在时间上不合理，并说明原因（如「长城单程通勤已占半天」）；
3. **提出替代方案**，例如：
   - 方案 A：延长至 2～3 天，并给出分拆建议；
   - 方案 B：保留用户最感兴趣的 N 个景点，其余标记为「建议改日 / 删减」；
4. **不强行输出一份看起来完整但不可执行的路书**。

**甄别维度（拟）：**

- 用户填写的入住/退房日期所覆盖的**游玩天数**（见 §4.1，与 `lodging` 联动）
- 每个景点建议停留时长（模型估算 + 用户输入）
- 景点间真实通勤时间 + **每日酒店往返**（`get_travel_time`，酒店作为锚点）
- 简单启发式上限（如单日有效游玩时长 8～10 小时，已扣除酒店往返）

---

### 2.2 情形二：景点名写错或不在目标城市

**场景示例：**

> 用户选择目的地 **北京**，但景点列表中出现：
> - 明显属于 **天津** 的景点（如「天津之眼」）
> - 明显属于 **上海** 的景点（如「外滩」）
> - 错别字导致的歧义地名（需结合 geocode 结果判断）

**期望行为：**

1. **合理怀疑**：对每个景点调用 `geocode_place` 后，比对解析结果与用户填写的 `city` / `country` 是否一致；
2. **先排除再规划**：疑似错城/错国的景点**不进入**最终 `recommendedOrder` 与 `roadbook`；
3. **明确提醒用户**：
   - 列出被排除的景点及原因（「解析地址位于天津市，与目标城市北京不符」）；
   - 请用户确认是写错了，还是确实打算跨城（若为后者，可提示调整目的地或拆分子行程）；
4. **避免强行编造**本地游览建议（如给上海的景点写「在北京上午去」）。

**甄别维度（拟）：**

- Geocoding 返回的 `formattedAddress` 与目标城市/国家匹配度
- 行政层级关键词（省/市/区）与常识冲突检测
- 可选：置信度低时标记为「待用户确认」，而非直接纳入路书

> **与 §3 的关系：** 内测 v1.0 仅支持「单一国家 + 单一城市 + 扁平景点列表」，会把用户**有意安排的跨城景点**误判为错城。内测 v1.1 拟通过**层级化目的地输入**（见 §3）从源头解决归属问题，§2.2 的甄别逻辑改为「景点是否属于用户声明的某一目的地」，而非强制单一城市。

## 3. 期望新功能：多目的地层级输入与布局重构

### 3.1 动机与场景

内测 v1.0 将「目标国家」「目标城市」各设为**单个文本框**，景点为**全局扁平列表**。这无法表达真实旅行中常见的多城甚至跨国组合：

| 场景 | 示例 | 内测 v1.0 的局限 |
|------|------|------------------|
| 同城多城（一国） | 中国 · **北京** + **天津** 一并安排 | 只能填一个城市，天津景点易被 §2.2 当成「错城」排除 |
| 跨国邻近城市 | 欧洲 · **丹麦哥本哈根** + **瑞典马尔默**（厄勒海峡大桥相连） | 跨国比中国跨省更常见，单城市模型完全不适用 |
| 一国多日环线 | 日本 · 东京 → 箱根 → 京都 | 无法表达景点归属哪一站 |

用户期望：**国家与城市可像景点一样「添加」**；每个景点明确挂在某一「国家 + 城市」下，避免张冠李戴与校验混乱。

### 3.2 交互与布局原则

**核心原则：目的地与景点放在同一区域，用层级结构表达归属关系。**

内测 v1.0 布局（简化）：

```
[ 目标国家 ]  [ 目标城市 ]     ← 各一个输入框，与景点分离
─────────────────────────
[ 景点网格 - 全局列表 ]        ← 景点不归属具体城市
```

内测 v1.1 拟议布局：

```
┌─ 住宿信息（v1.1：单酒店）──────────────────────────┐
│  酒店名称/地址  [ 北京饭店 / 东城区东长安街33号 ]   │
│  入住日期 [2026-08-01]   退房日期 [2026-08-04]     │
│  → 共 3 晚（游玩日数可自动推算）                    │
└────────────────────────────────────────────────────┘

┌─ 行程目的地与景点 ─────────────────────────────────┐
│                                                    │
│  ▼ 中国                                            │
│    ▼ 北京                          [+ 添加城市]    │
│        # │ 景点名      │ 地址（可选） │              │
│        1 │ 故宫        │              │  ×          │
│        2 │ 长城        │              │  ×          │
│        [+ 添加景点]                                 │
│                                                    │
│    ▼ 天津                          [× 删除城市]    │
│        # │ 景点名      │ 地址（可选） │              │
│        1 │ 天津之眼    │              │  ×          │
│        [+ 添加景点]                                 │
│                                                    │
│  [+ 添加国家/地区]                                  │
│                                                    │
│  ▼ 丹麦                                            │
│    ▼ 哥本哈根                      [+ 添加城市]    │
│        1 │ 小美人鱼雕像 │              │  ×          │
│        [+ 添加景点]                                 │
│                                                    │
│    ▼ 瑞典 · 马尔默                 [× 删除城市]    │
│        1 │ 马尔默城堡   │              │  ×          │
│        [+ 添加景点]                                 │
│                                                    │
└────────────────────────────────────────────────────┘
```

**操作层级：**

| 层级 | 用户操作 | 说明 |
|------|----------|------|
| **外层** | `+ 添加国家/地区` | 新增一个国家（或地区）块；块内可含多个城市 |
| **中层** | `+ 添加城市` | 在某一国家下新增城市；可删除整个城市块 |
| **内层** | `+ 添加景点` | 仅在当前城市下增删景点行；景点**天然归属**该城市 |

**与内测 v1.0 景点网格的关系：** 保留「序号 + 景点名 + 可选地址 + 删除」的行级交互，但**作用域从全局改为城市内**，避免改一处、乱一片。

### 3.3 数据模型（规划草案）

内测 v1.0 请求体（扁平）：

```json
{
  "country": "China",
  "city": "Beijing",
  "places": [{ "name": "故宫", "address": "" }]
}
```

内测 v1.1 拟议请求体（层级）：

```json
{
  "totalDays": 3,
  "lodging": {
    "mode": "single",
    "hotel": {
      "name": "北京饭店",
      "address": "东城区东长安街33号",
      "checkInDate": "2026-08-01",
      "checkOutDate": "2026-08-04"
    }
  },
  "destinations": [
    {
      "country": "China",
      "cities": [
        {
          "city": "Beijing",
          "places": [
            { "name": "故宫", "address": "" },
            { "name": "长城", "address": "" }
          ]
        },
        {
          "city": "Tianjin",
          "places": [
            { "name": "天津之眼", "address": "" }
          ]
        }
      ]
    },
    {
      "country": "Denmark",
      "cities": [
        {
          "city": "Copenhagen",
          "places": [{ "name": "小美人鱼雕像", "address": "" }]
        }
      ]
    },
    {
      "country": "Sweden",
      "cities": [
        {
          "city": "Malmö",
          "places": [{ "name": "马尔默城堡", "address": "" }]
        }
      ]
    }
  ]
}
```

**说明：**

- 每个 `place` 自带隐式 `country` + `city` 上下文，geocode / 校验 / 路书分段不再歧义；
- 跨国行程在数据层是自然表达，无需把「国家」强行压成单值；
- 若用户将哥本哈根与马尔默视为**同一行程区**（厄勒海峡区域），UI 上可仍分两国两城，由 LLM 在路书中做「区域联程」说明；后续可考虑「行程分区 / 枢纽」抽象，内测 v1.1 先不做过度设计。

### 3.4 对规划、地图与甄别逻辑的影响

| 模块 | 调整方向 |
|------|----------|
| **§2.2 错城甄别** | 改为：景点 geocode 结果是否落在**其声明的 city/country** 内；不再把「天津景点」在「含天津目的地」的行程里判错 |
| **§2.1 时间可行性** | 跨城通勤纳入总时长（如北京↔天津高铁、哥本哈根↔马尔默大桥）；可按「城市簇」或全局评估 |
| **Agent 路书** | 路书可按「Day / 城市段 / 站点」组织；跨城日需显式写出交通方式与时间范围 |
| **地图标点** | 可按城市块依次标点，或全局按推荐顺序标点；标记 title 中带上 `城市 · 景点名` |
| **Prompt** | 输入改为完整 `destinations` 树；要求模型识别联程合理性（如北欧跨国短途 vs 中国跨省长途） |

### 3.5 欧洲跨国 vs 中国跨城的产品提示（拟）

在 UI 或路书中，可对用户做轻量说明（非阻断）：

- **欧洲**：邻国城市短途联程较常见（如哥本哈根—马尔默），规划时可优先按地理邻近排序；
- **中国**：跨省/跨城距离往往更大，同日多城需格外谨慎，由 §2.1 可行性评估把关。

### 3.6 实现注意点（仅规划）

1. **向后兼容**：内测 v1.1 开发期可考虑将旧版单 `country/city/places` 自动包成单元素 `destinations` 数组，便于迁移；
2. **默认空状态**：至少保留「一个国家 + 一个城市 + 一行景点」的初始结构，与 v1.0 体验接近；
3. **删除保护**：删除城市块前确认（含其下所有景点）；删除国家块同理；
4. **总天数**：优先由 `lodging` 入住/退房区间推算，可手动覆盖；见 §4.3；
5. **页面其它区域**：Google Maps API、LLM 配置、智能路书展示位置可保持不变，仅**左侧输入区**做层级重构。

5. **页面其它区域**：Google Maps API、LLM 配置、智能路书展示位置可保持不变；**左侧输入区**做层级重构，并在其上方或下方增加 **§4 酒店住宿** 区块。

## 4. 期望新功能：酒店锚点与入住日期

### 4.1 动机

内测 v1.0 规划默认景点之间「裸连」，没有考虑游客**每天从酒店出发、晚上回酒店**的现实约束。这会导致：

- 路程估算偏乐观（忽略早晚酒店往返）；
- 路书缺少「一日闭环」感，不易执行；
- 游玩天数与真实预订 nights 脱节。

内测 v1.1 拟增加**酒店位置 + 入住起止日期**，并将酒店作为**每日行程的起点与终点**。

### 4.2 内测 v1.1 范围（刻意收敛）

| 能力 | v1.1 | 后续版本 |
|------|------|----------|
| 填写一家酒店 | ✅ | — |
| 入住日 / 退房日 | ✅ | — |
| 每日从该酒店出发并返回 | ✅ | — |
| 行程天数与入住区间对齐 | ✅ 建议自动推算 | — |
| 多酒店 / 换酒店 | ❌ | v1.2+ 按城市或日期切换酒店 |
| 酒店推荐 / 预订链接 | ❌ | 不做 |

**默认假设：整段行程住同一家酒店，不换宿。** 多城联程（§3）在 v1.1 仍可使用，但酒店默认视为一个固定大本营（适合「北京连住、当日往返天津」等）；若与用户意图冲突，由路书 `warnings` 提示「跨城日往返酒店较远，建议 v1.2 支持多酒店」。

### 4.3 交互与布局

酒店信息放在 **「行程目的地与景点」区块附近**（同一左侧面板），与层级目的地并列，避免与景点列表脱节：

```
┌─ 住宿信息（v1.1：单酒店）──────────────────────────┐
│  酒店名称 / 地址    [ 北京饭店 / 东城区 ...    ]    │
│  入住日期            [ 2026-08-01 ]                  │
│  退房日期            [ 2026-08-04 ]                  │
│  → 共 3 晚 / 建议按 3 个游玩日规划（自动推算，可覆盖）│
└────────────────────────────────────────────────────┘

┌─ 行程目的地与景点 ─────────────────────────────────┐
│  （§3 层级结构）                                    │
└────────────────────────────────────────────────────┘
```

**字段说明：**

| 字段 | 必填 | 说明 |
|------|------|------|
| `hotelName` | 建议填 | 便于路书展示与 geocode |
| `hotelAddress` | 与名称二选一 | 详细地址可提高定位精度 |
| `checkInDate` | 是 | 入住日（YYYY-MM-DD） |
| `checkOutDate` | 是 | 退房日，须晚于入住日 |

**天数关系（拟）：**

- 默认 `totalDays = checkOutDate - checkInDate`（按「晚数 = 游玩日数」处理，如 8/1 入住、8/4 退房 → 3 个完整游玩日）；
- 允许用户手动覆盖 `totalDays`，但若与入住区间明显不一致，触发 `validation.warnings`。

### 4.4 数据模型（规划草案）

在 §3.3 请求体上增加 `lodging`：

```json
{
  "totalDays": 3,
  "lodging": {
    "mode": "single",
    "hotel": {
      "name": "北京饭店",
      "address": "东城区东长安街33号",
      "checkInDate": "2026-08-01",
      "checkOutDate": "2026-08-04"
    }
  },
  "destinations": [ "...见 §3.3..." ]
}
```

**内部派生：**

- `lodging.hotel` 参与 geocode，得到 `hotelLatLng`，作为全局锚点；
- 每日路书逻辑节点：`酒店 → 景点₁ → … → 景点ₙ → 酒店`。

### 4.5 对规划、工具链与地图的影响

| 模块 | 调整方向 |
|------|----------|
| **工具 `geocode_place`** | 增加对酒店的一次 geocode（或在 Phase 1 与景点一并解析） |
| **`get_travel_time`** | 每日首段：`酒店 → 第一站`；末段：`最后一站 → 酒店`；中间段不变 |
| **§2.1 时间可行性** | 每日预算 = 可用游玩时长 − 当日酒店往返通勤 |
| **路书 `roadbook`** | 按 **Day 1…N** 组织；每天明确「自酒店出发 / 返回酒店」及时间范围 |
| **地图** | 酒店单独标记（如 `H`）；每日路线呈放射状往返（v1.1 可只画全日合并顺序） |
| **跨城日（§3）** | 当日仍从同一酒店出发返回；须在路书中标注长途通勤成本，必要时 warning |

### 4.6 路书展示（用户可见）示例

```
Day 1（8月1日）· 住：北京饭店
  08:30-09:00  酒店 → 故宫（驾车约 20-30 分钟）
  09:00-12:30  游览故宫（建议 3-3.5 小时）
  12:30-13:00  故宫 → 景山公园（约 10-15 分钟）
  ...
  17:30-18:00  最后一站 → 返回酒店（约 25 分钟）

Day 2（8月2日）· 住：北京饭店
  ...
```

> 仍为**时间段范围**，不精确到强制时刻；日期与 Day 对齐 `checkInDate` 起算。

### 4.7 实现注意点（仅规划）

1. **酒店可选但强烈推荐**：未填酒店时降级为 v1.0 式「景点直连」规划，并提示「填写酒店可获得更 realistic 的路书」；
2. **日期校验**：退房 ≤ 入住 → 表单错误；区间与 `destinations` 跨城安排冲突时由 Agent warning；
3. **与单酒店假设的边界**：北京+天津联程且单酒店在北京时，天津日往返路程必须计入可行性评估；
4. **后续 v1.2**：`lodging.mode: "multi"` + 每城/每段酒店列表，不在 v1.1 实现。

## 5. 方向性方案：CoT 反思 + Prompt 改进（综合 §2～§4）

针对 **§1 幻觉**、**§2 输入甄别**、**§3 多目的地** 与 **§4 酒店锚点**，建议在内测 v1.1 引入 **Chain of Thought（思维链）反思阶段**，并**整体重写 Agent 提示词**（`buildAgentSystemPrompt` / `buildAgentUserPrompt`），而非仅补丁式修改内测 v1.0 prompt。

### 5.1 为什么要 CoT，而不是只改 Prompt？

| 手段 | 能解决的问题 | 局限 |
|------|--------------|------|
| 只改 Prompt | 减少格式胡写、强化输出结构 | 对事实错误、跨城景点仍无力 |
| 只加规则引擎 | 天数/距离硬阈值 | 缺乏语义理解，误杀合理组合 |
| **CoT + 工具 + Prompt** | 先推理、再校验、再输出 | 实现成本较高，但贴合问题本质 |

**建议：分阶段推理，最后再输出用户可见的路书 JSON。**

---

### 5.2 拟议 Agent 流程（v1.1 草案）

```
用户输入（destinations 层级树、lodging 酒店与入住日期、游玩天数）
        │
        ▼
┌─────────────────────┐
│ Phase 0: 酒店解析    │  geocode 酒店；校验入住/退房与 totalDays；标记酒店锚点
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ Phase 1: 景点核验    │  geocode 每个景点；对照其声明的 city/country 校验归属
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ Phase 2: 可行性评估  │  按日估算：酒店往返 + 景点游览 + 景点间通勤；对比天数
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ Phase 3: CoT 反思    │  内部推理：幻觉风险、错城、超载、酒店过远日 warning
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ Phase 4: 路书生成    │  按 Day 输出；每日起终点均为酒店；JSON 路书
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ Phase 5: 自检（可选）│  对照核验结果与酒店闭环，矛盾则修正
└─────────────────────┘
```

**CoT 在本方案中的定位：**

- **不是**让用户阅读长篇推理过程（内测阶段可记录日志，默认不展示）；
- **是**强制模型在输出路书前完成「反思清单」，降低张口就来；
- 反思结论应体现在结构化字段中，例如：
  - `validation.excludedPlaces[]`（被排除景点及原因）
  - `validation.timeFeasibility`（是否超载、建议天数）
  - `validation.warnings[]`（不确定事实、需用户自行确认的事项）
  - `precautions[]`（仅写可核实或高置信度提醒）

### 5.3 Prompt 改进要点（v1.1 综合稿，规划未落地）

在 `llm.js` 中拟**新增** `buildAgentSystemPromptV11()` / `buildAgentUserPromptV11()`（或替换现有函数），核心增量如下。

#### A. System Prompt 增量

```
你是资深旅行规划师与路书撰写专家。

【输入形态】
- destinations：多国家/多城市层级树，每个景点归属明确城市；
- lodging：一家酒店（v1.1 仅 single），含名称/地址与入住、退房日期；
- 每日行程必须以该酒店为起点和终点（酒店→景点→…→酒店）。

【规划纪律】
1. 先 geocode 酒店与全部景点，再查询路程（含酒店↔景点）；
2. 按「尽量不走回头路」排景点顺序，跨城/跨国须尊重用户 destinations；
3. 按入住区间划分 Day 1…N，路书以「日期 + 酒店」为日框架；
4. 时间用范围描述，禁止精确到几点几分；
5. 禁止编造预约、内部区域、错误归属；不确定则标注待核实。

最终只输出 JSON，不要 markdown。
```

#### B. User Prompt 结构（拟）

1. 输出 `lodging` 与 `destinations` 完整 JSON（由后端注入）；
2. 工具使用说明（geocode 酒店 + 景点；travel_time 含酒店腿）；
3. 规划策略：不走回头路 + **每日酒店闭环**；
4. 输出 JSON Schema（见下）；
5. 硬性要求清单。

#### C. 输出 JSON Schema 增量（相对 v1.0）

在现有 `summary / placeSpotlights / roadbook / precautions` 基础上：

```json
{
  "lodgingSummary": {
    "hotelName": "北京饭店",
    "checkInDate": "2026-08-01",
    "checkOutDate": "2026-08-04",
    "nights": 3,
    "note": "全程固定入住，每日返回该酒店"
  },
  "dailyPlans": [
    {
      "day": 1,
      "date": "2026-08-01",
      "hotelName": "北京饭店",
      "segments": [
        {
          "type": "transit",
          "from": "酒店",
          "to": "故宫",
          "durationRange": "驾车约 20-30 分钟",
          "durationMin": 25
        },
        {
          "type": "visit",
          "placeName": "故宫",
          "visitTimeRange": "建议 3-3.5 小时",
          "visitDurationMin": 210
        },
        {
          "type": "transit",
          "from": "故宫",
          "to": "酒店",
          "durationRange": "返回酒店约 25-35 分钟",
          "durationMin": 30
        }
      ]
    }
  ],
  "roadbook": [ "...可与 dailyPlans 合并或互为镜像，实现时二选一..." ],
  "validation": { "...见 §6..." }
}
```

> **实现时建议：** `dailyPlans` 作为路书主结构（天然含酒店腿），`roadbook` 可保留为简化版或废弃，避免重复字段；文档阶段两者均列出供评审。

#### D. 事实纪律（继承并强化 §1）

- 禁止编造景点的内部区域、预约渠道、开放政策，除非属于公开常识；
- 不确定时使用「建议出发前查询官方信息」，而非肯定句；
- 景点介绍必须与其**真实地理位置、文化属性**一致，禁止张冠李戴；
- 高校、政府机关、私人区域默认**不可游览**，不得写入行程。

#### E. 输入甄别纪律（§2 + §3）

- 必须先完成酒店与景点地理核验，再排顺序；
- 景点须与其在 `destinations` 中声明的城市/国家一致，不一致的进入 `excludedPlaces`；
- 用户已声明的多城/跨国联程视为合法意图，不得当作「写错城市」排除；
- 时间超载时必须输出 `alternativeProposals`，不得假装一天可行。

#### F. 酒店锚点纪律（§4，新增）

- v1.1 **仅支持一家酒店**；不得擅自假设换宿或推荐未输入的第二家酒店；
- **每一天**的第一段交通必须来自酒店，最后一段必须返回酒店（除非当日无任何景点，则标注休息）；
- 使用 `get_travel_time` 时，必须包含 `酒店 → 首站` 与 `末站 → 酒店`；
- 跨城日若导致「酒店往返」过长，须在 `validation.warnings` 说明，并建议压缩景点或未来多酒店；
- `lodgingSummary.nights` 应与 `checkOutDate - checkInDate` 一致；`dailyPlans.length` 应与游玩日数一致。

#### G. CoT 反思清单（写入 prompt，模型内部步骤）

1. 酒店是否成功 geocode？位置与用户目的地是否合理？
2. 每个景点是否位于其声明的城市/国家？证据是什么？
3. 每个景点的介绍是否有编造风险？哪些应降级为「待核实」？
4. **按日分解**：每日「酒店往返 + 游览 + 景点间通勤」是否超过可用时长？
5. 全程是否满足不走回头路（或说明例外原因）？
6. 最终路书是否**每日闭环回酒店**？有无漏掉返回酒店的交通段？
7. 每条建议能否追溯到工具结果或公开常识？

## 8. 风险与待决问题

1. **Geocoding 本身可能歧义**（同名酒店、同名景点），错杀与漏杀如何平衡？
2. **CoT + 酒店腿 + 多城** 显著增加工具调用次数与 Token 成本。
3. **Qwen 等模型对复杂 schema + tool 的服从度**需实测（`dailyPlans` 是否与 `roadbook` 合并）。
4. **单酒店 vs 多城联程**：北京酒店 + 天津日是否默认允许？若允许，路书必须显式 warning，避免用户误以为轻松可行。
5. **入住日期与 totalDays**：以日期为准还是允许用户强制覆盖天数——需产品定稿。
6. **层级 UI 复杂度**：目的地 + 酒店 + 日期同屏，小屏是否需要分步向导。
7. **旧数据迁移**：无 `lodging` 时降级策略须在 UI 标明。

## 9. 与内测 v1.0 的差异小结

| 维度 | 内测 v1.0 | 内测 v1.1（规划） |
|------|-----------|-------------------|
| 目的地输入 | 单一国家 + 单一城市 | **可添加**的多国家/多城市层级树 |
| 景点归属 | 全局扁平列表 | **归属到具体城市** |
| 住宿 | 无 | **单酒店 + 入住/退房日期** |
| 每日动线 | 景点间直连 | **酒店出发 → 景点 → 回酒店** |

| 输入校验 | 无 | 按日可行性 + 归属校验 + 酒店往返 |
| 幻觉控制 | 单次 prompt | **Prompt v1.1 重写** + CoT + 自检 |
| 响应结构 | 路书为主 | `lodgingSummary` + `dailyPlans` + `validation` |
