# 内测 v1.3 前瞻规划：显式状态机 + 自动修复闭环

> 创建日期：2026-08-06
> 状态：**仅规划，尚未开发**
> 基线版本：[`内测-v1.2-改进规划.md`](./内测-v1.2-改进规划.md)（其上游为 [`内测-v1.1.0.md`](./内测-v1.1.0.md)）
> 终态参照：[`map-travel-agent-终极构想.md`](./map-travel-agent-终极构想.md)

本版本是从"单轮规划器"迈向"多轮自修复 Agent"的**地基版本**。v1.4（策略引擎）、v1.5（工具/校验扩展）、v1.6（记忆/局部重算）均依赖本版本落地的状态机与修复动作库。

---

## 1. 版本定位

| 维度 | v1.2（前置） | v1.3（本版本） |
|------|-------------|----------------|
| 流程形态 | 隐式串行调用，边界不清 | 显式状态机 `collect → build → plan → verify → repair → finalize / fallback` |
| 失败处理 | 以 warning 为主，部分裁剪 | 失败分类 → 触发修复动作 → 重跑校验 → 收敛 |
| 可靠性 | 基础错误处理 | 轮次上限 + 改善阈值 + 保底回退 + 全链路 trace 埋点 |

一句话目标：**把隐式流程升级为可收敛、可回退、可复盘的状态机，让"校验失败"从提示变成可自动执行的修复动作。**

---

## 2. 前瞻规划（本版本要实现的内容）

### 2.1 P0（必须）

1. **显式状态机落地**
   - 状态集：`collect_input → build_context → plan_initial → verify → repair → finalize`，异常兜底态 `fallback`。
   - 每个状态明确定义：进入条件、执行动作、退出条件、失败处理。
   - 状态流转由后端统一调度器驱动（`state-machine.js` 或等价模块），不再散落在 `server.js` 的顺序调用里。

2. **修复动作库（Repair Actions）**
   - 至少实现 4 类可执行修复动作：
     - `split_day`（拆天）：单日超载时把景点拆到相邻天；
     - `drop_lowest_priority`（降优先级删点）：删除优先级最低景点；
     - `swap_neighbor`（就近替换/换序）：调整相邻点顺序以减少折返；
     - `merge_day`（并天）：用户天数偏多时压缩空天。
   - 每个修复动作输入当前 `planData` + 失败原因，输出新的 `planData` + 修复说明。

3. **收敛控制（防死循环）**
   - 轮次上限 `MAX_REPAIR_ROUNDS`（默认 3）；
   - 改善阈值：连续 N 轮校验分数无改善则停止（默认 N=2）；
   - 失败分类回退：无法修复时进入 `fallback`，输出"保底可执行方案 + 明确未满足项"，而非报错终止。

4. **全链路 trace 埋点（本版本必须提前埋点）**
   - 每次状态流转、工具调用、校验结果、修复动作均写入结构化 trace（详见 §4）。
   - 埋点数据落地为可读取结构（内存 + 可选 JSON 落盘），供 v1.7 可观测体系直接消费。

### 2.2 P1（应做）

1. **校验结果结构化**
   - 校验器输出统一 `{ code, level, message, evidence }` 结构，`level ∈ {info, warn, error}`；
   - 每条校验结论必须带机器可判定的 `pass/fail` 与证据引用（geocode 结果、时长估算等）。

2. **修复链路差异记录**
   - 每轮修复前后记录 diff（哪些点被删/移动/换序），供最终"为什么改了路线"复盘。

### 2.3 P2（可选）

1. **状态机可视化调试端点**
   - 新增 `GET /api/debug/last-trace`，返回最近一次规划的完整 trace（仅内测环境开启）。

## 3. 关键方案设计

### 3.1 状态机定义

| 状态 | 进入条件 | 执行动作 | 退出条件 | 失败处理 |
|------|----------|----------|----------|----------|
| `collect_input` | 收到请求 | 归一化 destinations/places/lodging/约束 | 输入合法 | 输入非法 → `fallback` |
| `build_context` | 输入合法 | 预解析 geocode、构建酒店锚点、注入历史偏好（v1.6 接入） | 上下文就绪 | 关键 geocode 全失败 → `fallback` |
| `plan_initial` | 上下文就绪 | LLM + 工具生成候选顺序与 dailyPlans | 产出初版计划 | LLM/工具异常 → 重试或 `fallback` |
| `verify` | 有计划 | 运行校验器集合，输出结构化结论 | 全部 pass → `finalize`；有 error → `repair` | 校验器异常 → `fallback` |
| `repair` | 存在可修复 error | 选择并执行修复动作，重跑 verify | 收敛或达上限 | 达上限未收敛 → `fallback` |
| `finalize` | 校验通过 | 组装统一输出 schema | 输出完成 | — |
| `fallback` | 任一致命失败 | 输出保底方案 + 明确未满足项 | 输出完成 | — |

### 3.2 修复决策器（Repair Router）

- 输入：`verify` 输出的失败列表（按 code 分类）；
- 路由规则（示例）：
  - `TIME_OVERLOAD`（单日超载）→ `split_day` 或 `drop_lowest_priority`；
  - `CROSS_CITY_CONFLICT`（跨城冲突）→ `swap_neighbor` / 重新分天；
  - `HOTEL_LOOP_BROKEN`（酒店闭环断裂）→ 强制注入酒店腿或 `split_day`；
  - `TOO_MANY_EMPTY_DAYS`（空天过多）→ `merge_day`。
- 每轮只执行"预期收益最高"的一个修复动作，重跑校验后再决策，保证可追踪。

### 3.3 收敛与回退

```
round = 0
while round < MAX_REPAIR_ROUNDS:
    result = verify(plan)
    if result.pass: return finalize(plan)
    if no_improvement_for(N rounds): break
    plan = repair(plan, result.failures)
    round += 1
return fallback(plan, unresolved=result.failures)
```

## 4. 埋点设计（提前埋点，全链路 trace）

> 本版本是全项目埋点基线。后续所有版本的埋点都在此 schema 上扩展，v1.7 可观测体系直接消费。

### 4.1 统一 trace 事件结构

```json
{
  "traceId": "uuid",
  "requestId": "uuid",
  "ts": 1234567890,
  "stage": "verify",
  "eventType": "state_enter | state_exit | tool_call | validation | repair_action | fallback",
  "payload": { },
  "durationMs": 0,
  "status": "ok | warn | error"
}
```

### 4.2 必须埋的事件点（v1.3 基线）

| 事件点 | eventType | 关键 payload | 用途 |
|--------|-----------|--------------|------|
| 状态进入/退出 | `state_enter`/`state_exit` | `stage`、`durationMs` | 各阶段耗时、流转路径 |
| 工具调用 | `tool_call` | `tool`、`args摘要`、`ok/fail`、`durationMs`、`cacheHit` | 工具成功率、延迟、成本 |
| 校验结论 | `validation` | `code`、`level`、`pass`、`evidenceRef` | 违例率、失败类型分布 |
| 修复动作 | `repair_action` | `action`、`reason`、`beforeScore`、`afterScore`、`diff` | 修复收敛效果 |
| 回退 | `fallback` | `unresolved[]`、`reason` | 兜底触发率 |

### 4.3 埋点落地要求

- 埋点写入不得阻塞主流程（异步/批量）；
- 埋点失败**必须记录日志**，不得静默吞掉（遵循"无静默失败"约束）；
- 每次请求产出一条可导出的 trace（内存保留最近 N 条，内测可 JSON 落盘）。

## 5. 评价指标（验收标准，用于判定是否满足预期）

> 指标基于固定回归样例集（见 §6 检查清单）。v1.3 首次建立样例集与基线数值。

### 5.1 功能性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 状态机覆盖率 | 每次请求都完整走过定义态且无未定义跳转 | 100% |
| 修复动作可执行率 | 触发修复时能产出合法新 planData 的比例 | ≥ 95% |
| 收敛成功率 | 存在可修复 error 的样例最终收敛到 pass 的比例 | ≥ 80% |
| 兜底可用率 | 进入 fallback 时仍输出可执行保底方案的比例 | 100% |

### 5.2 可靠性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 死循环发生率 | 超过 MAX_REPAIR_ROUNDS 仍未终止的比例 | 0% |
| 平均修复轮次 | 收敛样例的平均 repair 轮数 | ≤ 2 |
| trace 完整率 | 请求产出完整 trace（含所有关键事件）的比例 | 100% |
| 无静默失败 | 埋点/工具/校验异常均有日志记录 | 100% |

### 5.3 一致性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 输出一致性 | `recommendedOrder`/`dailyPlans`/`roadbook` 三者景点集合一致 | 100% |
| 校验-结果一致性 | validation 结论与最终 dailyPlans 不矛盾 | 100% |

### 5.4 验收结论判定

- **通过**：5.1、5.2、5.3 全部达标，且回归样例集测试 100% 通过；
- **不通过**：任一 P0 指标未达标，需回炉修复后重测。

## 7. 风险与边界

1. 状态机重构可能影响现有同步/流式接口，需保证对外契约兼容（`plan` / `plan/stream`）；
2. 修复动作可能与"用户明确指定顺序"冲突，需保留用户强约束优先级；
3. 埋点数据量在高频调用下需控制体积（摘要化 payload）；
4. 收敛阈值需用真实样例调参，过严会误兜底，过松会浪费轮次。

## 8. 关键任务拆解（难点分解）

> 只拆解有难度、易踩坑的任务；简单任务（字段增删、文案）不在此列。每个难点给出子步骤 + 关键实现点 + 完成判据。

### 8.1 难点：显式状态机落地（最高优先）

**子步骤**
1. 抽象状态机内核：定义 `State` 枚举、`Transition(from, to, guard, action)`、统一 `Context` 对象（贯穿全流程携带输入/中间结果/trace）。
2. 实现调度器 `runStateMachine(context)`：循环取当前态 → 执行 action → 依 guard 决定下一态，直到 `finalize`/`fallback`。
3. 将现有 `server.js` 顺序逻辑逐态迁移（先照搬为各态 action，不改行为），保证对外接口 `plan` / `plan/stream` 契约不变。
4. 流式接口对接：每次 `state_enter/exit` 映射为一个 `progress` 事件，替换现有硬编码进度。
5. 回归对比：同一批样例，重构前后输出 diff 应为空（纯结构重构）。

**关键实现点**
- Context 单一数据源，禁止各态私存全局变量；
- guard 必须是纯函数（可单测）；
- 未定义的状态跳转直接抛错并进 `fallback`，不允许"隐式跳过"。

**完成判据**：状态机覆盖率 100%，重构前后输出零 diff，流式进度由状态流转驱动。

### 8.2 难点：修复动作库（每个动作单独拆）

**通用契约**：`repair(plan, failure, context) -> { newPlan, changeLog }`，纯函数、可单测、幂等。

| 动作 | 子步骤 | 完成判据 |
|------|--------|----------|
| `split_day` | ① 定位超载日 ② 选切分点（按顺序/就近）③ 生成新日并重排酒店腿 | 拆后每日不超载且景点不丢 |
| `drop_lowest_priority` | ① 计算各点优先级 ② 选最低且可删项 ③ 移除并记录到替代方案 | 删点后可行，被删点进 alternatives |
| `swap_neighbor` | ① 计算相邻交换的折返收益 ② 择优交换 ③ 复算段间时长 | 交换后折返程度不升高 |
| `merge_day` | ① 识别空/轻载日 ② 合并到相邻日 ③ 校验合并后不超载 | 天数压缩且不产生新超载 |

**关键实现点**：每个动作只做"一件事"，组合由决策器负责；所有动作产出 `changeLog` 供 diff 复盘。

**完成判据**：修复动作可执行率 ≥ 95%，每个动作有独立单测覆盖正常/边界。

### 8.3 难点：修复决策器 + 收敛控制

**子步骤**
1. 失败分类：把 verify 输出按 `code` 归类，映射到候选修复动作集合。
2. 收益预估：对候选动作预估 `afterScore`（可用轻量估算，不必真跑全量）。
3. 单步择优：每轮只执行收益最高的一个动作，重跑 verify。
4. 收敛判定：实现 `no_improvement_for(N)` 与 `MAX_REPAIR_ROUNDS`，命中即停并进 `fallback`。
5. 死循环防护测试：构造"无论怎么修都不可行"的样例，验证一定在上限内终止。

**关键实现点**：`beforeScore/afterScore` 用统一评分函数（与 v1.4 打分器共用接口，提前预留）；避免同一动作在两轮间来回抖动（记录已尝试动作指纹）。

**完成判据**：死循环发生率 0%，平均修复轮次 ≤ 2，收敛成功率 ≥ 80%。

### 8.4 难点：全链路 trace 埋点（供后续版本复用，必须一次做对）

**子步骤**
1. 定义 trace 写入器 `tracer`：`tracer.emit(event)`，内部异步缓冲 + 批量落地。
2. 在状态机内核统一织入 `state_enter/exit`（AOP 式，避免每态手写）。
3. 工具调用统一包裹 `withTrace(toolCall)`，自动记录 `durationMs/ok/cacheHit`。
4. 校验器与修复动作在返回处 emit `validation` / `repair_action`。
5. 提供 `getTrace(requestId)` 与内测落盘开关。

**关键实现点**：payload 摘要化（大对象存引用/裁剪）；埋点异常必须 `logger.warn` 不得静默吞（遵守无静默失败约束）；schema 版本号字段 `schemaVersion`，为 v1.7 演进留位。

**完成判据**：trace 完整率 100%，埋点开销对端到端延迟影响 ≤ 5%（v1.7 复核）。

## 9. 建议实施顺序（本版本内）

1. 先做 8.1 状态机内核 + 迁移（不改行为，纯重构，先绿测试）；
2. 再做 8.4 埋点织入（趁重构一并埋，避免二次改动）；
3. 然后 8.2 修复动作库（逐个动作 + 单测）；
4. 最后 8.3 决策器与收敛（把动作串成闭环）；
5. 全程用 §6 回归样例集守护，避免行为回退。
