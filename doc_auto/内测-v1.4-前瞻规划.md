# 内测 v1.4 前瞻规划：策略引擎（多策略 + 打分兜底）

> 创建日期：2026-08-06
> 实现日期：2026-08-10
> 状态：**P0 + P1 + P2 已实现 + OI-1 根治**（实现落地记录见 §10）
> 基线版本：[`内测-v1.3-前瞻规划.md`](./内测-v1.3-前瞻规划.md)（依赖其状态机与修复动作库）
> 终态参照：[`map-travel-agent-终极构想.md`](./map-travel-agent-终极构想.md)

本版本把规划策略从"单一不走回头路"升级为"多策略模板 + 后端打分器兜底"，让 LLM 只负责解释文案，最终排序由规则层保证可控与可解释。

---

## 1. 版本定位

| 维度 | v1.3（前置） | v1.4（本版本） |
|------|-------------|----------------|
| 策略能力 | 固化"尽量不走回头路" | 2~3 个可切换策略模板 + 权重打分 |
| 排序决策 | LLM 主导，规则兜底 | 规则打分器主导排序，LLM 负责解释 |
| 可解释性 | 有 routeStrategy 文案 | 明确"选了哪个策略、为什么、得分构成" |

一句话目标：**用可解释的打分器决定最终顺序，支持用户在"省时/少换乘/经典打卡"等策略间切换。**

---

## 2. 前瞻规划

### 2.1 P0（必须）

1. **策略模板化**
   - 至少 3 个策略：`fastest`（总通勤最短）、`least_transfer`（最少换乘/跨城）、`classic`（高优先级景点优先打卡）；
   - 默认策略可配置（建议默认 `classic`）；
   - 前端提供策略选择入口，请求体新增 `strategy` 字段。

2. **后端打分器（Scoring Engine）**
   - 分数函数：`score = w1·总时长 + w2·换乘次数 + w3·折返程度 + w4·优先级命中率`（各项归一化）；
   - 不同策略使用不同权重组合 `w`；
   - 打分器对候选顺序集合排序，取最优；LLM 输出仅作候选与文案来源，最终顺序以打分器为准。

3. **策略解释输出**
   - 输出 `strategyExplanation`：所选策略、关键得分项、为什么优于次优方案。

### 2.2 P1（应做）

1. **策略与修复动作联动**
   - 修复阶段（v1.3）产生新候选时，复用当前策略权重重新打分，保证修复后仍符合用户策略取向。

2. **多方案对比输出**
   - 输出 A/B 两套（如 `fastest` vs `classic`）供用户对比，标注适用条件。

### 2.3 P2（可选）

1. **交通模式偏好接入打分**
   - 引入 `driving/transit/walking` 偏好作为打分项（依赖 v1.2 的 transit 分段数据）。

## 3. 关键方案设计

### 3.1 策略权重表（示例）

| 策略 | w_总时长 | w_换乘 | w_折返 | w_优先级 | 适用场景 |
|------|---------|--------|--------|----------|----------|
| `fastest` | 高 | 中 | 高 | 低 | 时间紧、通勤敏感 |
| `least_transfer` | 中 | 高 | 中 | 低 | 带娃/老人、怕折腾 |
| `classic` | 低 | 低 | 中 | 高 | 首次到访、必打卡优先 |

### 3.2 打分器流程

```
candidates = generate_orderings(places, constraints)   # 来自 LLM 候选 + 规则扩展
for c in candidates:
    c.score = weighted_score(c, strategy.weights)
best = argmin(candidates.score)
explanation = explain(best, second_best, strategy)
```

- 候选集合规模需控制（剪枝/启发式），避免组合爆炸；
- 打分项全部基于 §4 埋点中的真实工具数据（时长/换乘），不允许模型臆断。

## 4. 埋点设计（在 v1.3 trace 基线上扩展）

### 4.1 新增事件与字段

| 事件点 | eventType | 新增 payload | 用途 |

## 5. 评价指标（验收标准）

### 5.1 功能性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 策略生效率 | 用户指定策略时最终顺序符合该策略取向的比例 | ≥ 90% |
| 打分器覆盖率 | 最终顺序由打分器产出（非 LLM 直接采纳）的比例 | 100% |
| 解释完整率 | 输出含 `strategyExplanation` 且引用真实得分项的比例 | 100% |

### 5.2 质量指标（相对 v1.3 基线对比）

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 平均总通勤时长（fastest） | 相比 v1.3 默认策略下降幅度 | 下降 ≥ 10% |
| 平均换乘次数（least_transfer） | 相比 v1.3 下降幅度 | 下降 ≥ 15% |
| 优先级命中率（classic） | 高优先级景点被保留在前段的比例 | ≥ 90% |

### 5.3 稳定性指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 打分耗时 | 单次打分器额外耗时 | ≤ 300ms（候选剪枝后） |
| 组合爆炸防护 | 候选集合规模受控（不超过上限 K） | 100% |

### 5.4 验收结论判定

- **通过**：5.1 全达标，5.2 至少 2/3 达标，5.3 全达标，回归样例集通过；
- **不通过**：策略生效率或打分器覆盖率不达标必须回炉。

## 7. 风险与边界

1. 打分权重是主观取向，需用真实样例反复调参，避免"数值最优但体验差"；
2. 候选生成若过度依赖 LLM，可能引入不稳定，需规则层扩展候选；
3. 多方案对比会增加 token 与计算成本，需评估性价比；
4. 策略与用户强约束（指定顺序）冲突时，用户约束优先。

## 8. 关键任务拆解（难点分解）

> 只拆解有难度的任务。本版本最硬的是"候选生成 + 剪枝"与"打分器"两块。

### 8.1 难点：候选顺序生成 + 剪枝（防组合爆炸，本版本最硬）

**子步骤**
1. 候选来源分两路：① LLM 输出的推荐顺序（1~N 个）；② 规则扩展（如最近邻、按优先级、按城市分组内排序）。
2. 剪枝策略：
   - 先按城市分组，组间顺序用最近邻定序，组内再排列，降低搜索空间；
   - 设候选上限 `K`（如 ≤ 20），超出用启发式截断；
   - 去重（顺序等价的候选只保留一个）。
3. 对每个候选计算所需 `travel_time`，复用 v1.5/工具缓存，避免重复调用。
4. 输出候选集合 + 每个候选的原始度量（总时长、换乘数、折返度、优先级命中）。

**关键实现点**：段间时长计算是主要成本，务必缓存 `(a,b)->duration`；候选生成与打分解耦（生成只产度量，打分只算分）。

**完成判据**：候选集合规模 ≤ K（100% 受控），打分器额外耗时 ≤ 300ms。

### 8.2 难点：打分器与权重设计

**子步骤**
1. 度量归一化：把总时长/换乘/折返/优先级命中各自归一化到 `[0,1]`（需定义各自的 min-max 或饱和函数）。
2. 实现 `weighted_score(metrics, weights)`，权重来自策略模板。
3. 权重调参：用 §6 回归样例，人工标注"期望最优顺序"，反推/校准权重使打分器选择与期望一致。
4. 策略模板固化：`fastest/least_transfer/classic` 三套权重定稿。

**关键实现点**：折返度需可量化（如"实际总里程 / 最优近似里程"或方向回退次数）；归一化边界要用真实样例统计，避免个别极值主导分数。

**完成判据**：各策略在专项样例上的质量指标达标（省时 -10%、少换乘 -15%、classic 命中 ≥ 90%）。

### 8.3 难点：策略与 v1.3 修复动作联动

**子步骤**
1. 抽出统一评分接口（v1.3 收敛控制的 `afterScore` 与本版本打分器共用同一函数）。
2. 修复动作产出新候选后，用"当前策略权重"重新打分，而非默认权重。
3. 回归验证：修复后方案仍符合用户策略取向（如 least_transfer 修复后换乘不升高）。

**完成判据**：策略生效率 ≥ 90%，且修复不破坏策略取向。

## 10. 实现落地记录（2026-08-10）

本轮实现 **P0 + P1 + P2 全部条目**，并根治 v1.3 §13 登记的 **OI-1**。对外接口契约（`POST /api/agent/plan`、`/api/agent/plan/stream`）保持兼容，新增字段均为**增量**；默认策略 + 默认交通偏好（`driving`）下输出与 v1.3 等价。

> 实施前经用户确认两项关键决策：① **`CROSS_CITY_CONFLICT_THRESHOLD` 维持为 2**（不下调），OI-1 改由方向 B 从分天源头根治；② **A/B 对比采用「用户所选策略 vs 次优策略」**。

### 10.1 新增/改动模块

| 模块 | 职责 | 关键导出 |
|------|------|----------|
| `scoring.js`（新增） | 统一评分器（纯函数、无外部依赖） | `normalizeMetrics`、`scoreMetrics`（→ `{score, breakdown, normalized}`）、`clamp01`、`DEFAULT_BOUNDS` |
| `agent-planner.js` | 候选生成/剪枝、择优、聚类分天、按日口径、解释、对比、交通偏好 | `generateCandidateOrders`、`chooseBestOrder`（含 breakdown/secondBest）、`clusterOrderByCity`、`computeDailyMetrics`、`buildStrategyExplanationDetail`、`compareStrategies`、`applyTransportPreference`、`scoreRouteDetailed`、`buildPriorityOrder`、`orderSignature` |
| `repair.js` | 策略×修复联动 | `rescorePlanWithStrategy` |
| `tracer.js` | 埋点扩展（schema 1.4.0） | 复用 `emit` 承载 `strategy_select`/`scoring`/`alternative_compare`；`repairAction` 增加 `strategy`/真实 `afterScore` |
| `server.js` | 状态机接线（候选/择优/聚类/对比/埋点/联动） | `CANDIDATE_LIMIT`、`buildRepairContext.scoreOrder`、`assembleResult` 输出新字段 |
| `index.html`/`app.js` | 前端策略对比展示 + 出行方式偏好入口 | `transportSelect`、「策略对比」区块 |

### 10.2 P0（对应 §2.1）

- **策略模板化**：沿用 v1.2 三策略（`fastest`/`least-transfer`/`classic`）+ 请求体 `strategy` + `/api/strategies` + 前端选择器（已具备）。
- **后端打分器**：`scoring.scoreMetrics` 将 `总时长/换乘/折返/优先级命中` 归一化到 `[0,1]` 后加权（priority 作减项），输出 `scoreBreakdown`；`chooseBestOrder` 消费候选集合择优，打分器主导排序、LLM 仅作候选来源与文案。
- **候选生成 + 剪枝**：`generateCandidateOrders` 多路候选 → 去重 → 上限 `K`（默认 20，`CANDIDATE_LIMIT` 覆盖）。
- **策略解释输出**：`strategyExplanation{ strategy, chosenBreakdown, secondBest, scoreGap, reason }`，含「为什么优于次优方案」。

### 10.3 P1（对应 §2.2）

- **策略×修复联动**：修复上下文注入 `scoreOrder`（当前策略权重），`repair.rescorePlanWithStrategy` 对修复后方案重打分，写入 `repair_action.afterScore`，保证修复不破坏策略取向。
- **A/B 多方案对比**：`compareStrategies` 输出 `strategyComparison{ primary（用户策略）, runnerUp（差异最大的其他策略，含 tradeoff）}`；独立于 v1.3.1 天数 `alternativePlan`，前端概览下渲染「策略对比」块。

### 10.4 P2（对应 §2.3）

- **交通模式偏好接入打分**：请求体 `transportPreference: driving|transit|walking`，`applyTransportPreference` 以权重乘子作用于打分（`driving` 为默认零改动）；前端「出行方式偏好」选择器。

### 10.5 OI-1 根治（对应 v1.3 §13 方向 B + C）

- **方向 B（cluster-then-assign）**：`clusterOrderByCity` 在 `plan_initial` 选出最优顺序后一次性按城市稳定聚类，作为**唯一顺序源**向下游（enrichedPlaces/分天/planData/roadbook）一致传导；「先聚类、再连续分块」使**任意策略**（含 fastest 的城市交错顺序）下同城景点同日，同日跨城降为 0。
- **方向 C（按日打分口径）**：`computeDailyMetrics` 以「按日分组 + 每日回酒店」口径统计同日跨城，输出到 `routeMetrics.crossCityByDay`/`crossCityWithinDay`（仅上报，**不改** `CROSS_CITY_CONFLICT` 阈值，遵用户决策）。

### 10.6 埋点扩展（对应 §4）

- schema `1.3.0 → 1.4.0`；新增 `strategy_select`（策略/是否用户指定/交通偏好）、`scoring`（候选数/最优分/得分构成）、`alternative_compare`（chosen/rejected/scoreGap/tradeoff）三类事件，复用统一 emit 通道，异常不静默。

### 10.7 测试与回归

- 新增 `tests/scoring.test.js`（归一化边界/命中率/得分构成/饱和/交通偏好乘子，7 例）；扩展 `tests/agent-planner.test.js`（候选剪枝/K 上限/聚类分天/按日口径/解释/对比）与 `tests/repair.test.js`（策略联动、`rescorePlanWithStrategy` 空态无静默失败）。
- 全量 `node --test` 通过 **87/87**（原 67 + 新增 20）；`package.json` test 脚本纳入 `scoring.test.js`。手工 smoke：服务正常启动、`/api/strategies` 200。

### 10.8 与后续版本衔接

- 统一评分接口（`scoreRouteDetailed`/`scoring.scoreMetrics`）为 v1.5/v1.6 复用；`crossCityByDay` 为终极构想「全局层跨城分天」度量预留；trace schema 1.4.0 供 v1.7 可观测体系消费。
