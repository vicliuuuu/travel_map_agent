## 0. 范围调整说明（2026-08-11，PENDING 决策）

> **长期记忆及其依赖项暂缓（PENDING），本版本实际交付范围收敛为「局部重算 + 多酒店/换酒店」。**

**背景**：当前应用部署在 **Render**（对应 GitHub 仓库自动部署），其默认文件系统是**临时的（ephemeral）**——每次重新部署或服务重启，容器内写入的文件都会被清空。因此原方案「把用户偏好写成本地 JSON 文件持久化」在该部署形态下**无法可靠留存**（撑不过一次重新部署），后端也不应在运行时回写 GitHub 仓库。

**决策**：长期记忆功能 **PENDING**，待确定**可靠的持久化存储方案**后再启动。候选方向（后续单独决策）：
- 外部数据库（Render PostgreSQL / 云端 KV 如 Upstash Redis）；
- Render 持久磁盘（Persistent Disk，付费）；
- 前端 `localStorage`（不占后端，但换设备/浏览器不通用）。

**受影响（一并 PENDING）的条目**：因均依赖记忆存储/注入，下列条目同步暂缓：
- §2.1.1 长期记忆存储与注入
- §2.1.3 记忆写入冲突治理
- §2.2.2 偏好可解释注入
- §2.3.1 偏好自动学习
- §3.1 记忆数据结构、§4 中 `memory_read/memory_write/preference_inject` 埋点、§5 中记忆相关指标、§8.3 记忆写入冲突治理

**本版本仍推进（ACTIVE）的条目**：不依赖记忆、可独立交付：
- §2.1.2 局部重算（Incremental Replan）
- §2.2.1 多酒店 / 换酒店支持
- §4 中 `incremental_replan` 埋点、§8.1 局部重算影响域分析、§8.2 多酒店按日闭环

## 2. 前瞻规划

### 2.1 P0（必须）

1. **长期记忆存储与注入** —— **【PENDING，见 §0；待定持久化存储方案后启动】**

   - 注入时机：`build_context` 阶段（v1.3 状态机）注入偏好，影响策略默认值与打分权重。

2. **局部重算（Incremental Replan）** —— **【ACTIVE，本版本核心】**

   - 影响域分析：仅重算受影响的日与相邻段，其余日程与已确认结果保持不变；
   - 局部重算后仍走 v1.3 的 verify/repair，但作用域收敛到受影响范围。

3. **记忆写入冲突治理** —— **【PENDING，依赖记忆存储】**
   - 偏好冲突（本次行为与历史偏好矛盾）时的合并策略：本次显式操作优先，历史偏好作为默认建议；
   - 记忆写入必须记录来源与时间，可回溯、可撤销。

2. **偏好可解释注入** —— **【PENDING，依赖记忆注入】**

## 3. 关键方案设计

### 3.1 记忆数据结构（示例）

```json
{
  "userId": "u_123",
  "preferences": {
    "pace": "slow",
    "transport": ["metro", "walk"],
    "interests": ["museum", "food"],
    "taboos": ["early_start"],
    "hotelSwitchAversion": true
  },
  "meta": { "updatedAt": 0, "source": "explicit|learned", "revisable": true }
}
```

### 3.2 局部重算流程

```
onChange(event):
    affected = analyze_impact(event, currentPlan)   # 受影响的日/段
    subPlan = replan(affected, context)             # 仅重算受影响域
    merged = merge(currentPlan, subPlan)
    verify(merged, scope=affected)                  # 局部校验
    if fail: repair(scope=affected)                 # 局部修复
    return merged
```

- 未受影响的日/段直接复用，节省调用与保持稳定；
- 局部重算与全量重算共用同一状态机，仅作用域不同。

## 8. 关键任务拆解（难点分解）

> 本版本最硬的是"局部重算影响域分析"（判错就会全局失配）与"多酒店按日闭环"。

### 8.1 难点：局部重算影响域分析（本版本最硬）

**子步骤**
1. 建立依赖图：把行程建模为"日 → 段 → 点"，记录每个点所在日、前驱/后继点、所依赖的酒店腿。
2. 变更影响传播规则：
   - `remove_place`：影响所在日 + 该点前后段的重连；
   - `add_place`：影响插入目标日（可能触发该日超载 → 连锁到相邻日）；
   - `move_place`：影响源日与目标日两处；
   - `change_day`：影响涉及的相邻日。
3. 计算 `affectedScope`（最小受影响日集合），冻结其余日的结果。
4. 只对 affectedScope 重跑 plan/verify/repair，再 merge 回全局。
5. 一致性兜底：merge 后做一次"跨日边界"轻校验（酒店腿、跨城衔接），防止局部改动破坏边界。

**关键实现点**：影响传播必须"宁可多算一日也不能漏"——漏算会导致全局失配；`reusedRatio` 要真实统计未重算部分，作为增量效果证据。

**完成判据**：未受影响日程保持不变 100%；复用率 ≥ 60%；耗时/调用较全量下降 ≥ 40%。

> 状态：**已实现（2026-08-11）**，见 §12 落地记录（本版本聚焦 `remove_place` / `move_place` 两类改点，纯本地重算不重调地图/LLM）。

### 8.2 难点：多酒店按日闭环

**子步骤**
1. 输入建模：每个酒店锚点带 `effectiveDays`（生效日区间/夜次），构建"日 → 当日酒店"映射。
2. 每日闭环按当日酒店生成首尾腿（首段 `hotel_d → first`，末段 `last → hotel_d`）。
3. 换酒店日处理：定义换酒店当天的行李转移腿（旧酒店 → 新酒店），并计入当日时间预算。
4. 与 v1.5 往返成本校验联动：换酒店日往返成本单独评估。

**关键实现点**：换酒店当天是最易出错的边界（既要退房又要入住又要游览），需专门样例；无当日酒店映射时回退为"无酒店闭环"逻辑。

**完成判据**：多酒店样例每日按当日酒店正确闭环 100%，换酒店日不丢行李转移腿。

### 8.3 难点：记忆写入冲突治理

**子步骤**
1. 定义冲突：本次显式操作与历史偏好矛盾（如历史"少走路"，本次主动加了远距徒步点）。
2. 合并策略：本次显式操作生效于本次；是否更新长期偏好需"确认后固化"（P2 自动学习同理）。
3. 写入审计：记录 `source(explicit/learned)`、`updatedAt`、可撤销标记。
4. 提供撤销/导出接口（隐私合规）。

**完成判据**：冲突按"显式优先"正确处理 100%；记忆可撤销/可导出。

## 11. 多酒店输入模型重构（2026-08-11 讨论，设计已定、暂未开发）

> 本节细化 §2.2.1 / §8.2 的输入层设计。多酒店功能的核心前提是"重构输入模型"——把景点与酒店拆开，并给每家酒店加入住/离店日期。

### 11.1 动机

现有输入模型是"单酒店时代"的设计：一个扁平的**景点列表**，每行带"景点/酒店"类型下拉；若某行标为酒店，后端 `splitLodgingFromPlaces` 将其拆出作为**唯一**酒店锚点（`lodging.mode = "single"`）。该模型假设"全程只住一家"，无法表达多酒店与按日安排，需重构。

### 11.2 重构后的输入模型

- **景点与酒店分离为两个独立区块**：
  - `景点列表`：纯景点，**删除每行的"景点/酒店"类型下拉**（分离后冗余）；
  - `酒店列表`：独立区块，可增删多家酒店。
- **酒店整体为可选项（隐私考量）**：客人可不透露住宿；酒店列表留空 → 全程走"无酒店闭环"逻辑（现已存在）。
- **每家酒店带入住/离店日期**：`{ name, address, checkInDate, checkOutDate }`；`checkInDate/checkOutDate` 后端 schema 已有字段，本次在前端显式暴露并支持多条。

### 11.3 已定决策（2026-08-11）

| 决策点 | 结论 |
|--------|------|
| 时间粒度 | **仅到日期**（如 08-01 入住、08-03 离店），不做时刻级 |
| 换酒店日归属 | 旧酒店离店日 = 新酒店入住日时，**当天算新酒店**：白天行程结束回新酒店；早上从旧酒店出发，**新增"旧酒店 → 新酒店"行李转移腿**并计入当日时间预算 |
| 空档期（某天无任何酒店覆盖） | **两者都要**：该天退化为"无酒店闭环"（不强制回酒店）**且**输出一条提醒"第 N 天无酒店覆盖"，让用户自行补充 |

### 11.4 生效日映射机制

```
每家酒店 [checkInDate, checkOutDate]
        ↓ 展开为覆盖的夜次/日
构建 "第 N 天 → 当天酒店" 映射（dayToHotel）
        ↓
每日闭环用当天酒店算首尾腿（首:酒店→首景点  末:末景点→酒店）
换酒店日：额外插入"旧酒店→新酒店"行李转移腿
无覆盖日：退化无酒店闭环 + 提醒
```

### 11.5 后端改造点（预估）

- `buildDefaultLodging`：`mode` 从固定 `"single"` 扩展为支持多酒店列表（如 `mode: "multi"` + `hotels: [...]`），保留单酒店向后兼容；
- `splitLodgingFromPlaces`：景点与酒店分离后，此"从景点里拆酒店"的逻辑可简化/下线（改由独立酒店区块直接传入）；
- 分天闭环（`buildDailyPlansFromPlanData` / `verifyHotelClosure`）：由"单一 hotelName"改为"按当天 `dayToHotel` 取酒店"；
- 校验：新增日期合法性校验（离店早于入住、日期区间重叠/空档），空档期发提醒。

### 11.6 边界与校验清单

- [ ] 离店日期早于入住日期 → 报错/提示；
- [ ] 两家酒店日期区间重叠 → 提示（同一晚住两家不合理）；
- [ ] 存在空档日 → 退化无酒店闭环 + 提醒（§11.3）；
- [ ] 酒店只填名称不填日期 → 退化为"全程该酒店"（兼容单酒店旧行为）；
- [ ] 酒店列表为空 → 全程无酒店闭环。

## 12. 实现落地记录：局部重算（Incremental Replan，§8.1）（2026-08-11）

本轮实现 §8.1「局部重算」。已定范围（与用户对齐）：支持 **删除（`remove_place`）+ 移到另一天（`move_place`）** 两类改点；受影响天做「重新排序（打分）+ 重算闭环 + 校验」；**纯本地计算，不重新调用地图/LLM**（也因后端无状态、拿不到上次的坐标缓存）。

**架构约束与取舍**
- 后端无状态（Render 每请求独立），故局部重算不依赖服务端会话：由前端把「当前 `planData` / `dailyPlans` / `enrichedPlaces` / `lodging` / 策略」回传，后端据此重建 `placeMetaMap` 与通勤查表。
- 通勤时长复用：从当前 `dailyPlans` 的 transit 段建 `travelLookup`（已知相邻双向命中），新相邻段走打分器的兜底口径（同城/跨城默认值），避免重新调用外部工具——这是「省调用、耗时下降」的关键。

**后端（`replan.js`，新增）**
- `analyzeImpact(changeEvent, planData)`：影响域分析，「宁可多算一日也不能漏」——删=所在天；移=源天 + 目标天（去重升序）。
- `applyChange(planData, changeEvent)`：不改入参地应用删除/移动，返回新 `planData`。
- `buildTravelLookupFromDailyPlans(dailyPlans)`：从既有分段构建通勤查表（双向命中，未知返回 null）。
- `reoptimizeAffectedDays(...)`：仅对受影响天用 `generateCandidateOrders` + `chooseBestOrder` 内部重排序，未受影响天原样返回。
- `incrementalReplan(...)`：编排上述步骤并计算 `reusedRatio =（总天数 - 受影响天数）/ 总天数`。

**后端（`server.js`）**
- 新增 `POST /api/agent/replan`（走限流）与 `buildAgentReplanPayload`：重建 meta/lookup → `incrementalReplan` → 用 `buildDailyPlansFromPlanData` 重组 dailyPlans → `verifyHotelClosure` + `runVerifiers`（体力校验）→ 回传 `planData/dailyPlans/recommendedOrder/routeMetrics/lodgingSummary/validation/affectedDays/reusedRatio/traceId`。
- 缺少/非法 `changeEvent`、空 `planData` 返回 400（不静默失败）。

**埋点（`tracer.js`）**
- 新增 `incremental_replan` 事件（`changeType/affectedScope/reusedRatio/dayCount`），复用统一 emit 通道；schema 升至 **1.6.0**。

**前端（`app.js` / `styles.css`）**
- 「按日行程」主方案每个景点新增「删除此点 / 移到第 N 天」控件（备选方案只读）；事件委托到 `#itineraryResult`。
- `performReplan(changeEvent)`：调 `/api/agent/replan`，把结果并回 `state.lastAgentResult` 后重渲染路书 + 重绘地图，状态栏显示「仅重算第 X 天、复用 Y%」；概览区新增局部重算回执条。

**测试（`tests/replan.test.js`，9 例）**

## §13. 实现落地记录：天数估算重做（逐日装箱 + 单日预算随体力强度联动）

**背景**：双城用例仍被误估 1 天；进一步核查发现「单链 10h 上限」与「体力强度设置」**从无关联**——选 7h 档位，天数估算/超载判定仍按写死的 10h。

**核查结论（两套独立的数）**
- 单日 **10h(600 分钟)** 硬编码在三处（`server.js` 估算 / `agent-planner.js evaluateTimeFeasibility` / `verifier.js DAY_BUDGET_MIN`），管「游玩+通勤」总量；
- 体力档位仅产出 `maxVisitMinutes`(5/7/9h)+`maxVisits`(4/6/8)，是**纯游玩**上限（不含通勤），且**只**用于独立的 `PHYSICAL_OVERLOAD` 提醒，不参与天数/超载预算。二者量纲不同、互不影响。

**修复①逐日装箱（`server.js` 重写 `estimateNaturalDaysAndSubset`）**
- 从 1 天起按 `splitPlacesIntoCityAlignedDays` 切分，取「每天都可行」的最小天数为 `naturalDays`。
- 每天须**同时**满足体力档位三约束：①纯游玩（含 0.1 疲劳、每天重置）≤ `maxVisitMinutes`；②景点数 ≤ `maxVisits`；③游玩+段间通勤+**当天各自的酒店往返** ≤ 单日总预算×slack。
- 通勤走混合口径（新增 `makeHybridLegMin`：真实 `travelCache` 优先 → 坐标 haversine 兜底 → fallback），酒店往返每天各算一次（主酒店坐标近似，跨城日自然更贵）。
- `compactPlaces` 亦按同一约束在 `reqDays` 内按城市软对齐装箱，溢出计入 `droppedPlaces`。签名由 `(orderedPlaces, requestedDays, averageTravelMin)` 改为 `(orderedPlaces, requestedDays, options)`。

**修复②单日预算随体力强度缩放（用户确认 8/10/12h + 15% 冗余）**
- `verifier.js`：体力档位新增 `dayBudgetMin`（轻松 480 / 标准 600 / 硬核 720）；新增并导出 `DAY_BUDGET_SLACK=0.85`。
- `agent-planner.js`：`evaluateTimeFeasibility` 新增 `options.dayBudgetMin/slack`（缺省 600、slack=1，向后兼容）。
- `verifier.js runVerifiers`：`TIME_OVERLOAD` 改用 `checks.dayBudgetMin/dayBudgetSlack`，evidence 与文案改为「可用预算」。
- `server.js`：`v15Checks` 与估算调用点均从 `getPhysicalPreset(...)` 透传 `dayBudgetMin` + `DAY_BUDGET_SLACK`，三处口径统一；`day_estimate` 埋点补充 `dayBudgetMin/dayBudgetSlack/maxVisitMinutes/maxVisits`。

**效果**：双城 7 点 → 估 **2 天**（1 天时疲劳后纯游玩 819>420 且 7>6 不可行）；同一 4 点单城，标准=1 天、轻松=2 天，验证强度联动。

**测试**：新增 `tests/day-estimate.test.js`（8 例）+ 更新 `tests/verifier.test.js` 的 `getPhysicalPreset` 断言。全量 `node --test` **159/159** 通过。

修改时间：2026-08-11 18:20 (UTC+8)
