# 内测 v1.5 前瞻规划：工具层扩展 + 校验层扩展

> 创建日期：2026-08-06
> 实现日期：2026-08-11
> 状态：**P0 + P1 + P2 已实现**（实现落地记录见 §10）
> 基线版本：[`内测-v1.4-前瞻规划.md`](./内测-v1.4-前瞻规划.md)
> 终态参照：[`map-travel-agent-终极构想.md`](./map-travel-agent-终极构想.md)

本版本把工具层从"geocode + 驾车时长"扩展为**可插拔的多事实源**（营业时间、天气、拥堵），并把校验层从"时间/归属"扩展到**闭馆风险、体力强度、酒店往返成本**，让规划贴近真实约束。

---

## 1. 版本定位

| 维度 | v1.4（前置） | v1.5（本版本） |
|------|-------------|----------------|
| 工具层 | geocode + travel_time（+v1.2 transit） | 追加营业时间 / 天气 / 拥堵，统一可插拔接口 |
| 校验层 | 时间超载 + 跨城归属 + 酒店闭环 | 追加闭馆风险 / 体力强度 / 往返成本 |
| 事实可信度 | 依赖模型知识 | 外部事实统一标注来源与"待核实"状态 |

一句话目标：**让规划能"知道景点几点关门、当天会不会下雨、路会不会堵、走不走得动"，并把这些变成可判定的校验项。**

## 2. 前瞻规划

### 2.1 P0（必须）

1. **可插拔工具接口规范**
   - 统一 tool 抽象：`{ name, schema, invoke(args), errorCode, cacheKey }`；
   - 支持工具热插拔（配置开关决定启用哪些工具），未启用工具不影响主流程；
   - 统一错误码标准化 + 幂等缓存（相同 args 命中缓存）。

2. **营业时间工具（opening_hours）**
   - 查询景点开放/关闭时间；
   - 供校验层判断"按当前排程到达时是否已闭馆"。

3. **校验层扩展**
   - `opening_risk`：到点预计时间晚于闭馆时间 → error/warn；
   - `physical_load`：单日累计步行/游览时长超阈值 → warn（阈值可按偏好调整）；
   - `hotel_return_cost`：每日回酒店往返成本过高 → warn + 触发修复建议。

### 2.2 P1（应做）

1. **天气工具（weather）**
   - 查询目的地当天/近期天气；
   - 输出风险提示（暴雨/高温/暴雪），供 precautions 与后续动态重排（v1.6+）使用。

2. **拥堵指数工具（congestion）**
   - 对高峰时段段间通勤给出拥堵修正系数，修正 travel_time 估算。

3. **外部信息来源标注**
   - 所有外部事实输出必须带 `source`、`fetchedAt`、`verifyState(verified/unverified)`；
   - 未核实信息在路书中明确标注，防幻觉。

### 2.3 P2（可选）

1. **工具降级策略**
   - 某工具不可用时自动降级（如天气不可用则跳过天气校验并标注），保证主流程不中断。

## 3. 关键方案设计

### 3.1 工具插件注册表

```json
{
  "tools": {
    "geocode_place": { "enabled": true },
    "get_travel_time": { "enabled": true },
    "opening_hours": { "enabled": true, "provider": "google_places" },
    "weather": { "enabled": true, "provider": "..." },
    "congestion": { "enabled": false }
  }
}
```

- 调度器按注册表动态装配可用工具；
- 每个工具独立超时/重试/缓存配置。

### 3.2 校验器扩展（复用 v1.3 结构化输出）

| 校验器 | code | 触发条件 | 建议修复动作 |
|--------|------|----------|--------------|
| 闭馆风险 | `OPENING_RISK` | 预计到达晚于闭馆 | 提前该点顺序 / 改日 |
| 体力强度 | `PHYSICAL_OVERLOAD` | 单日时长/步行超阈值 | split_day / 降密度 |
| 往返成本 | `HOTEL_RETURN_COST` | 单日回酒店往返占比过高 | 换序 / 换酒店建议（v1.6） |

- 新增校验器全部产出 v1.3 定义的 `{ code, level, pass, evidence }` 结构，可直接被修复决策器消费。

## 4. 埋点设计（在 v1.3/v1.4 trace 基线上扩展）

### 4.1 新增事件与字段

| 事件点 | eventType | 新增 payload | 用途 |
|--------|-----------|--------------|------|
| 新工具调用 | `tool_call` | `tool ∈ {opening_hours,weather,congestion}`、`provider`、`cacheHit`、`degraded` | 各工具成功率/延迟/缓存命中/降级率 |
| 新校验结论 | `validation` | `code ∈ {OPENING_RISK,PHYSICAL_OVERLOAD,HOTEL_RETURN_COST}` | 新增违例类型分布 |
| 外部事实来源 | `fact_source` | `source`、`fetchedAt`、`verifyState` | 事实可信度审计 |
| 工具降级 | `tool_degrade` | `tool`、`reason`、`fallbackUsed` | 降级触发率与稳定性 |

### 4.2 埋点要求

- 每个外部事实必须可追溯来源与时间；
- 工具降级必须埋点并记录日志（不静默）；
- 缓存命中率单独统计，评估成本优化效果。

## 7. 风险与边界

1. 营业时间/天气数据存在区域覆盖不均，需降级策略兜底；
2. 拥堵与天气为动态数据，路书应标注"时间窗"而非绝对结论；
3. 新增校验阈值需真实调参，避免高误报打扰用户；
4. 多工具调用推高成本，缓存与开关是关键控制手段。

## 8. 关键任务拆解（难点分解）

> 本版本最硬的是"可插拔工具接口"（抽象要一次做对，后续工具都靠它）与"闭馆风险校验"（涉及时间轴推算）。

### 8.1 难点：可插拔工具接口规范（架构决定后续扩展成本）

**子步骤**
1. 定义 `Tool` 抽象：`{ name, schema, invoke(args), normalizeError(e), cacheKey(args), timeoutMs, enabled }`。
2. 实现工具注册表 `ToolRegistry`：按配置装配 enabled 工具，提供 `get(name)` 与 `listEnabled()`。
3. 统一调用包装 `invokeTool(name, args)`：内部做超时、重试、缓存查/写、错误码标准化、trace 埋点（复用 v1.3 `withTrace`）。
4. 把现有 `geocode_place` / `get_travel_time` 改造为符合该抽象的插件（回归验证行为不变）。
5. 新工具（opening_hours 等）按同一抽象接入，零侵入主流程。

**关键实现点**：错误码标准化是重点——不同 provider 的错误要映射到统一枚举（`RATE_LIMIT/NOT_FOUND/TIMEOUT/PROVIDER_ERROR`），供降级与校验决策；cacheKey 要对 args 归一化（大小写/空格/去音符）。

**完成判据**：新增工具不改动状态机主流程即可接入；缓存命中率 ≥ 60%。

### 8.2 难点：闭馆风险校验（时间轴推算）

**子步骤**
1. 由 dailyPlans 推算每个点的"预计到达时刻"：从当日起点（酒店/首点）时刻起，累加游览时长 + 段间通勤。
2. 拉取 opening_hours，解析为当日 `[open, close]` 区间（注意跨天、午休、周几差异）。
3. 判定：预计到达 > close → `OPENING_RISK(error)`；接近 close（如剩余 < 游览时长）→ warn。
4. 输出证据：`{到达时刻, 闭馆时刻, 差值}`，供修复动作（提前顺序/改日）使用。

**关键实现点**：到达时刻推算依赖"当日出发基准时刻"，需定义默认（如 09:00）或从偏好读取；营业时间数据缺失时降级为 warn 并标注 unverified，不可当作 pass。

**完成判据**：构造的闭馆冲突样例检出率 ≥ 90%，正常样例误报率 ≤ 10%。

### 8.3 难点：工具降级策略

**子步骤**
1. 分级定义：工具不可用时，是"跳过并标注"（天气）还是"用保守估计"（拥堵系数取 1.0）还是"致命失败进 fallback"（geocode 全失败）。
2. 在 `invokeTool` 捕获标准错误码后按分级执行降级，emit `tool_degrade`。
3. 校验层感知降级：被降级工具对应的校验项标注为 unverified，不计入硬失败。

**完成判据**：任一非致命工具不可用时主流程 100% 仍产出方案；降级均有埋点与日志（不静默）。

## 11. v1.5.1 增量：工具真接入 + 高危 bug 修复（2026-08-11）

v1.5.0 是骨架（工具默认关闭、weather/congestion 为空壳）。本轮把工具真正接入并默认开启，修复开启后会导致结论错误的高危项，并按用户反馈把体力强度做成可选。

### 11.1 工具真接入 + 默认开启

- **默认开启**：三工具开关默认改为 `true`；修复 weather/congestion「传 `fetch:null` 导致开关设 true 也启用不了」的假开关问题。
- **Google Weather API**：`buildGoogleWeatherProvider` 按经纬度取每日预报 → 降水/高低温风险 → 并入 `precautions`；`fetchWeatherNotes` 按天（首景点坐标 + 实际日期）查询、命中缓存；降级则标注 unverified 不进注意事项。
- **拥堵（内置高峰启发式）**：`tools.peakHourCongestionFactor`（早/晚高峰 ×1.4、肩部 ×1.15），在 `computeArrivalTimeline` 按出发时刻放大通勤，直接作用于闭馆判定；无需额外 API，也支持后续注入 Directions 实时路况 provider。

### 11.2 高危 bug 修复（开启后一开就会错的）

1. **通勤缺失按 0 算 → 闭馆漏报**：`computeArrivalTimeline` 对缺失/为 0 的 transit 段改用 `DEFAULT_TRANSIT_FALLBACK_MIN=30`（与 `evaluateTimeFeasibility` 口径一致）。
2. **营业时间/天气按"今天"查而非实际游玩日期**：`buildPlaceDateMap`（景点→实际日期，来自 `checkInDate`+天序），opening_hours/weather 均按当天查询。
3. **假开关**：见 11.1。

### 11.3 体力强度用户可选（对应 §2.1.3 阈值可按偏好调整）

- `verifier.PHYSICAL_PRESETS` + `getPhysicalPreset`：`easy/standard/hardcore` → 5h/4、7h/6、9h/8；请求体 `physicalPreference`（默认 standard），前端「体力强度偏好」下拉。回酒店往返维持标准档 35%。

### 11.4 测试

- 全量 `node --test` 通过 **114/114**（v1.5.0 的 109 + 新增 5：高峰启发式/拥堵默认启用/通勤兜底/拥堵修正/体力档位映射）。

### 11.5 仍待用户实测（无法离线验证）
