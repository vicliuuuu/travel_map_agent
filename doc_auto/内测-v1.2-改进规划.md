# 内测 v1.2 改进规划

> 创建日期：2026-08-03  
> 实现日期：2026-08-06  
> 状态：**P0 + P1 已实现**（P2 受控攻略检索暂缓）  
> 基线版本：[`内测-v1.1.0.md`](./内测-v1.1.0.md)

本文档针对 v1.1.0 的线上化、策略能力与路书可执行性缺陷给出 v1.2 规划方向，并在文末记录本轮实现落地情况。

---

## 1. 可实现性判断（先结论）

### 1.1 公网可访问

**结论：合理且可实现，建议作为 v1.2 P0。**

- 当前架构已是前后端分离的轻量形态，可直接部署到云环境；
- 关键改造不在功能本身，而在**安全与稳定性**：
  - LLM/Maps key 迁移到后端环境变量；
  - 增加限流、超时、熔断、日志与错误追踪；
  - 配置域名、HTTPS 与 CORS 策略。

### 1.2 策略方法提升（不止“不走回头路”）

**结论：合理且可实现，建议 v1.2 P1。**

- 现有策略过单一，易出现“地理顺路但体验不佳”的结果；
- 可扩展为“策略组合 + 权重打分”：
  - 最少折返；
  - 最少跨城次数；
  - 最短总通勤时长；
  - 高优先级景点优先；
  - 交通模式偏好（地铁/步行/驾车）。

### 1.3 路书过于笼统（“请以实时导航为准”过多）

**结论：合理且可实现，建议 v1.2 P0。**

- 你给的样例（哥本哈根市政厅 -> 马尔默竞技场）需要跨国轨道交通，确实应拆成多段时间：
  - 市政厅 -> 哥本哈根中心站（步行/地铁）；
  - 哥本哈根中心站 -> 马尔默中心站（火车）；
  - 马尔默中心站 -> 竞技场（公交/步行）；
- 这类多段信息可由 Google Maps Directions 的 `transit` 模式返回（含 `steps` 与 `transit_details`）；
- 路书正文可精简展示，地图可展示总路线，详细分段作为折叠信息或 tooltip。

### 1.4 酒店闭环不稳定

**结论：合理且可实现，建议 v1.2 P0。**

- 问题本质是“闭环约束未作为硬规则进入最终排程器”；
- 需把“每日首段从酒店出发、末段回酒店”从提示词要求升级为后端结构化硬约束，禁止模型绕开。

## 2. v1.2 目标范围

### 2.1 P0（必须）

1. **公网部署可用**
   - 生产部署脚手架（Dockerfile / env / 启动配置）；
   - Key 后端托管；
   - 基础限流与观测。

2. **交通时间更具体**
   - 增加 `transit` 路径查询；
   - 路书段落从“估计提示”升级到“可执行分段时长”；
   - 优先减少“请以实时导航为准”空泛描述。

3. **酒店闭环硬约束**
   - 后端 daily planner 必须在每日日程首尾注入酒店腿（有酒店锚点时）；
   - 若无法闭环，返回明确 warning 与替代方案。

### 2.2 P1（应做）

1. **策略引擎升级**
   - 支持 2~3 个可切换策略模板（例如“省时优先”“少换乘优先”“经典打卡优先”）；
   - 在路书中解释“为什么选这个策略”。

2. **分段交通解释**
   - 对跨城段输出“站点-站点”结构（起点站、终点站、预计时长、换乘次数）；
   - 地图保持简洁，路书支持折叠展开详情。

### 2.3 P2（可选）

1. **攻略增强（谨慎）**
   - 引入受控网页检索，仅用于补充开放时间/购票提醒；
   - 所有外部信息必须标注“来源时间与待核实状态”。

## 3. 关键方案设计

### 3.1 公网化方案

#### 后端安全改造

- 前端不再传 `llmApiKey`；
- 后端读取 `LLM_API_KEY`、`MAPS_API_KEY`；
- 新增 `ALLOWED_ORIGINS` 与 `RATE_LIMIT_*` 配置。

#### 部署建议

- 平台任选：Render / Railway / Fly.io / 阿里云 ECS；
- 交付项：
  - `Dockerfile`
  - `.env.example`
  - `deploy.md`

### 3.2 交通分段方案（解决“请以实时导航为准”）

#### 路径查询层

- 对同城短途：优先 `driving/walking/transit` 组合评估；
- 对跨城段：强制查询 `transit`，读取 Google 返回的 `steps`：
  - 步行段；
  - 轨道交通段（线路名、发到站）；
  - 换乘段。

#### 输出结构建议

新增字段（示意）：

```json
{
  "transitBreakdown": [
    {
      "from": "哥本哈根市政厅",
      "to": "马尔默竞技场",
      "mode": "transit",
      "totalDurationMin": 72,
      "legs": [
        { "type": "walk", "from": "市政厅", "to": "哥本哈根中心站", "durationMin": 12 },
        { "type": "train", "line": "Öresundståg", "from": "København H", "to": "Malmö C", "durationMin": 36 },
        { "type": "bus/walk", "from": "Malmö C", "to": "马尔默竞技场", "durationMin": 24 }
      ]
    }
  ]
}
```

### 3.3 策略引擎方案

- 从“单一 prompt 策略”升级为“策略参数 + 后端打分器”：
  - `strategy=fastest`
  - `strategy=least-transfer`
  - `strategy=classic`
- 分数函数由“总时长、换乘次数、回头路程度、优先级命中率”组成；
- LLM 只负责解释和文案，最终排序由规则层兜底。

### 3.4 酒店闭环稳定性方案

- 当存在酒店锚点时：
  - 每日 `segments[0]` 强制 `hotel -> firstPlace`；
  - 每日最后一段强制 `lastPlace -> hotel`；
- 若闭环导致单日超载：
  - 触发拆天或删点；
  - 输出替代方案（保持可执行优先）。

## 4. 针对你给的 v1.1 样例问题的修复目标

样例：哥本哈根市政厅、小美人鱼雕像、马尔默竞技场。

v1.2 目标行为：

1. 自动识别跨国跨城段（哥本哈根 -> 马尔默）；
2. 对该段采用 `transit` 分段估时，不再只给泛化提示；
3. 若 1 天可行，则明确建议压缩到 1 天；
4. 若 1 天不可行，则给出删点版本与完整版本两套方案；
5. 若设置酒店锚点，则每日闭环回酒店（或明确说明不闭环原因与代价）。

## 6. 风险与边界

1. Google Maps Transit 在部分区域数据粒度不一致；
2. 跨国交通时刻为动态数据，路书需标注“时间窗”而非绝对时刻；
3. 攻略检索若不做来源控制，可能再次引入幻觉风险；
4. 公网部署后需重点关注 API 成本与滥用防护。

## 8. 实现落地记录（2026-08-06）

本轮已实现 **核心三块代码功能 + 公网部署脚手架**，密钥保持 keep 模式（前端仍可传，未传时后端环境变量兜底），默认策略为 `fastest`。

### 8.1 已实现

- **策略引擎（P1）**：`agent-planner.js` 新增策略模板（`fastest` / `least-transfer` / `classic`）、路线打分器（`computeRouteMetrics` + `scoreRoute`）、贪心候选生成（`buildGreedyOrder`）与择优（`chooseBestOrder`）。后端在「LLM 建议顺序」与「策略贪心候选」间打分择优，并在 `routeStrategy` 中解释所选策略与路线指标（总通勤/跨城/折返）。前端 `index.html` 新增策略下拉，`app.js` 透传 `strategy` 并展示策略标签与指标。
- **跨城交通分段（P0）**：`server.js` 对最终顺序的跨城相邻段调用 Google Directions `transit`，`agent-planner.parseTransitLegs` 解析步行/轨交/换乘为 `legs`，输出 `transitBreakdown`；按日行程的交通段填入可执行分段时长并支持折叠展开，替代“请以实时导航为准”。
- **酒店闭环硬约束（P0）**：`buildDailyPlansFromPlanData` 改为结构化强制闭环（每日首段 `hotel->首站`、末段 `末站->hotel`），新增 `closedLoop` 标记与 `verifyHotelClosure` 告警，写入 `validation.lodgingWarnings` 与 `validation.hotelClosure`。
- **公网部署（P0）**：新增 `package.json`、`Dockerfile`、`.dockerignore`、`.env.example`、`deploy.md`；`server.js` 增加 CORS 白名单（`ALLOWED_ORIGINS`）、基础限流（`RATE_LIMIT_*`）、`GET /api/strategies` 发现接口与密钥环境变量兜底（`applyEnvKeyFallback`，非破坏性）。

### 8.2 测试

- `tests/agent-planner.test.js` 新增策略打分/择优、贪心聚类、`parseTransitLegs`、酒店闭环、transit 填充等用例；
- 全量 `node --test` 通过（31/31）；
- 手工 smoke：`GET /api/strategies` 返回策略列表、限流第 3 次请求返回 `429`、静态资源 200。

### 8.3 密钥处理（keep 模式 + .env 嵌入）

- 密钥统一放后端 `.env`（`.gitignore` 已忽略，不进 git）；前端保留可输入接口不变。
- 请求未携带 key 时后端回退到 `.env`（`applyEnvKeyFallback`）；
- 新增 `GET /api/public-config` + 前端预填：`EXPOSE_KEYS_TO_FRONTEND=true` 时把 `.env` 密钥下发到前端输入框做自测预填（仍可手改）；
- **正式上线设 `EXPOSE_KEYS_TO_FRONTEND=false`**，前端不接收密钥，由每个用户自行填写。
