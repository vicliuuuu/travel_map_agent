# Map Travel Agent 终极构想（Vision Draft）

文档日期：2026-08-03  
适用范围：`map` 项目后续版本规划（v1.2+）

---

## 1. 愿景定义

理想的 `map travel agent` 不只是“生成一段行程文案”，而是一个可执行、可校验、可修复的旅行决策系统：

- 用户给出目标与约束（时间、预算、偏好、体力）；
- Agent 基于地图与真实路网能力生成行程；
- Agent 对可行性进行自动校验；
- Agent 在发现冲突后自动重排并收敛到可落地方案；
- 输出不仅可读，而且可直接执行（按日、按段、带依据）。

一句话定义：

> **Map Travel Agent = 以地图事实为基础、以可执行性为目标、以闭环修复为核心的旅行副驾驶。**

---

## 2. 终极能力边界（What / Not What）

### 2.1 What（应具备）

- 真实地理约束：路线、时长、跨城交通、营业时间、天气风险；
- 多轮闭环：`plan -> verify -> repair -> finalize`；
- 解释能力：每个关键决策附“为什么”；
- 局部重算：用户改一个点，只重算受影响部分；
- 风险兜底：自动给出替代方案（A/B/C）。

### 2.2 Not What（不应止步于）

- 只输出一次性“看起来合理”的路线文本；
- 不做校验、只做美化描述；
- 发现冲突仅报错不修复；
- 改动一个条件就全局推翻重做。

---

## 3. 标准 Agent 八步流程在本项目的映射

### 3.1 Goal Intake（目标接收）

- 输入：目的地层级（国家/城市/景点）、点位类型（景点/酒店）、游玩天数、用户偏好。
- 目标：将自然语言诉求转为结构化任务目标与硬约束集合。

### 3.2 Context Building（上下文构建）

- 汇总所有景点及地理声明信息；
- 建立酒店锚点（可选）；
- 读取已有规划历史（如用户已删除/保留的景点偏好）。

### 3.3 Planning（任务分解与计划）

- 全局层：先做跨城市分组与天数分配；
- 日内层：再做当天顺序与时间段规划；
- 交通层：补齐段间交通与回酒店闭环策略。

### 3.4 Tool Selection（工具选择）

- `geocode`：校验地点语义和城市归属；
- `route/directions`：评估段间真实交通时间；
- 可扩展工具：天气、营业时间、拥堵趋势。

### 3.5 Action Execution（执行）

- 调用工具获取证据；
- 生成 `recommendedOrder`、`dailyPlans`、`validation`；
- 输出统一 schema，保证前后端渲染一致。

### 3.6 Verification（校验）

- 天数可行性：每天总时长是否超载；
- 地理一致性：声明城市与解析结果是否冲突；
- 酒店闭环：日程起终点是否符合设定。

### 3.7 Reflection / Repair（反思与修复）

- 识别失败类型：时间超载 / 跨城冲突 / 交通不可达；
- 触发自动修复策略：拆天、降优先级、就近替换；
- 重跑校验并比较前后版本差异，直到收敛或达上限。

### 3.8 Delivery / Memory（交付与记忆）

- 最终输出：可执行路书 + 风险说明 + 替代路线；
- 长期记忆：沉淀用户偏好（节奏、交通方式、兴趣标签）；
- 形成复盘记录：本次为何调整、下次如何更优。

---

## 4. 理想系统结构（六层模型）

1. **输入层（Input Layer）**  
   结构化接收用户目标、约束、偏好与点位数据。

2. **规划层（Planning Layer）**  
   进行跨城分天、日内排序、段间衔接。

3. **工具层（Tool Layer）**  
   对接地图、交通、天气、营业时间等事实源。

4. **校验层（Validation Layer）**  
   对可行性、冲突、风险进行规则化判定。

5. **修复层（Repair Layer）**  
   失败后自动重排并再次校验，形成闭环。

6. **记忆层（Memory Layer）**  
   沉淀用户长期偏好与高频决策模式。

---

## 5. 输出协议（建议）

建议输出采用“主结果 + 校验结果 + 替代方案”的固定结构：

- `plan`: 推荐路线、按日安排、每段交通与时长；
- `validation`: 可行性、冲突明细、风险等级；
- `alternatives`: 不同偏好下的替代路线（少走路/省时/亲子）；
- `explanations`: 关键决策解释（为什么是这个顺序）。

目标：保证“机器可解析 + 人可理解 + 前端可稳定渲染”。

---

## 6. 从当前状态到终态的三阶段路线图

### 阶段 A（基础闭环）

- 建立显式状态机：`collect -> plan -> verify -> repair -> finalize`；
- 增加自动修复重试（有上限）；
- 将校验失败转化为可执行修复动作，而非纯 warning。

### 阶段 B（策略增强）

- 区分失败类型并路由不同工具；
- 引入跨城交通分段策略（同城游览与城际迁移分开求解）；
- 输出 A/B 方案并标注适用条件。

### 阶段 C（个性化与鲁棒性）

- 接入用户偏好记忆；
- 引入天气/营业时间动态重排；
- 增加可观测性指标与回放能力（可复盘每次修复链路）。

---

## 7. 终态验收标准（Definition of Done）

- 功能性：对复杂多城输入可稳定产出可执行计划；
- 正确性：校验结果与最终日程一致，冲突可追踪；
- 自主性：发现不可行时可自动修复，不依赖人工重提问；
- 可解释性：每个关键调整均有明确理由；
- 可维护性：输出 schema 稳定，测试覆盖核心闭环路径。

---

## 8. 对本项目的定位结论

当前 `map` 项目已具备 Agent 雏形（LLM + 地图工具 + 结构化输出 + 基础校验），  
下一步核心不是“再加字段”，而是**补齐闭环修复与策略执行能力**，从“单轮规划器”升级为“多轮自修复 Agent”。
