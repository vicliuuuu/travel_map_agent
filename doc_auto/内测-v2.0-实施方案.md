本方案把 v2.0 前瞻规划落地为**可执行实施计划**。经评估：v2.0 的「对话体验层」在现有代码基础上**全部可实现**；仅两处按既有 PENDING 边界降级——**长期记忆**（无持久盘）与**跨会话回放/门禁**（依赖落盘）。因此本次采用**变体 A（内存态 v2.0）**：对话体验全做，记忆与跨会话落盘顺延。

## 0. 范围与边界（变体 A）

### 0.1 本版本做（ACTIVE）

- 多轮自然语言对话，先理解后规划（对话-规划双状态机）。
- 约束抽取 + 主动澄清（含澄清预算上限）。
- 对话内局部修改 → 复用 v1.6 局部重算（`POST /api/agent/replan` 已交付）。
- 每步结论绑定证据（基于**单次会话内的内存 trace**，无需落盘）。
- 解释性对话（基于 v1.4 打分 + 内存 trace）。
- 多方案对话推荐（复用 v1.4 `compareStrategies`）。
- 对话维度埋点（内存态，schema 升至 2.0.0）+ 单次评测扩到对话维度。

### 0.2 本版本降级 / 不做（PENDING，承接 v1.6/v1.7 §0）

| 条目 | 处理 | 根因 |
|------|------|------|
| 长期记忆填默认 | 降级为**合理默认 + 一次结构化确认** | 无持久盘（v1.6 §0） |
| 跨会话回放复盘 | 降级为**单次会话内可复盘** | trace 落盘 PENDING（v1.7 §0） |
| baseline 门禁 | 降级为**单次评测跑通出指标** | 落盘 PENDING（v1.7 §0） |
| 语音/多模态（P2） | 不做 | 远期可选 |

> 关键澄清：**证据绑定（§8.3）与解释性对话（§2.2）不依赖落盘**——它们只消费单次请求/会话内的内存 trace（已具备），因此**照做，不降级**。真正需要落盘的仅是「事后跨会话回放」。

## 1. 架构

```
[前端对话面板]
      │  对话历史 + 当前草稿(constraints draft)
      ▼
POST /api/agent/dialog（新：对话编排端点）
      │  由 dialog.js 对话状态机驱动
      ├── 抽取/澄清：intake.js（新）
      ├── present（首次出行程）：复用 buildAgentPlanPayload（已有）
      ├── refine（对话内改）：复用 buildAgentReplanPayload / POST /api/agent/replan（已有）
      ├── 多方案：复用 compareStrategies（已有）
      └── 解释：复用 scoreRouteDetailed / buildStrategyExplanationDetail（已有）
      ▼
返回 { action, reply, draft, plan?, evidence[] }
```

- **对话层**只管「聊到哪 + 抽取 + 何时规划」；**规划/改行程**直接复用现有函数，不重写。
- 双状态机共享同一 `requestId/traceId`，保证会话内可复盘。

## 3. 新增模块

### 3.1 后端

- **`intake.js`（新）**：约束抽取与草稿管理（尽量纯函数，可单测）。
  - `extractConstraints(dialogHistory, draft)`：走 LLM function-calling，输出结构化约束 + 每字段置信度 + `missing[]`。
  - `mergeConstraints(prev, delta)`：增量合并草稿（新值覆盖/补充，不丢历史）。
  - `isRequiredComplete(draft)`：必填判定（目的地 + 景点 + 天数）。
  - `decideClarify(draft, turnIndex, budget)`：澄清决策（仅必填缺失或低置信才追问；超预算则用默认继续并记 `assumptions`）。
  - `buildPlanInputFromDraft(draft)`：草稿 → 现有 plan 端点入参（destinations/places/hotels/totalDays/visitMinutes/strategy/transport/physical）。
- **`dialog.js`（新）**：对话状态机（复用 `state-machine.js` 引擎）。
- **`POST /api/agent/dialog`（新端点）**：编排一轮对话，返回下一步动作。

### 3.2 埋点（`tracer.js` 扩展，内存态）

新增 5 类事件，schema `1.7.0` → `2.0.0`：`dialog_turn` / `constraint_extract` / `clarify` / `dialog_refine` / `evidence_ref`（payload 见 §5）。

### 3.3 前端

- 对话面板（消息流 + 输入框 + 「结束对话」）；present 后在同界面展示路书，每条关键结论旁可展开「证据 / 为什么」。
- refine：用户口语化改需求 → 调 replan → 只更新受影响天并回话解释。
- **安全边界**：对话**绝不询问/抽取/记录** API key（Google Maps / Qwen）、Base URL、model；这些仅走原表单/环境变量，且不进对话上下文。

## 4. 对话-规划双状态机

```
DialogState: greet → gather → clarify → confirm → present → refine
                                  │                            │
                                  └────> PlanStateMachine(v1.3)<┘   (present: buildAgentPlanPayload)
                                                                    (refine : buildAgentReplanPayload)
```

| 状态 | 职责 | 复用 |
|------|------|------|
| greet | 打招呼、说明会问哪些、提示先在表单填 API | — |
| gather | 收集目的地/景点/天数/可选偏好 | `intake.extractConstraints` |
| clarify | 仅必填缺失或低置信才追问，受澄清预算约束 | `intake.decideClarify` |
| confirm | 结构化确认「我理解你要 X，对吗」 | — |
| present | 首次出完整行程 | `buildAgentPlanPayload` |
| refine | 对话内局部修改 | `buildAgentReplanPayload` |

- **澄清预算**：单会话澄清问题数默认上限 6（可配）；超限用默认值继续并在 `confirm` 里说明假设。
- **必填**：目的地、景点、天数；其余（游玩时长/策略/交通/体力）用合理默认（fastest / driving / standard / 90min）。

## 5. 埋点设计（对话维度，内存态，schema 2.0.0）

| 事件 | eventType | payload | 用途 |
|------|-----------|---------|------|
| 对话轮次 | `dialog_turn` | `turnIndex`、`dialogState`、`intent` | 对话流转/轮次分析 |
| 约束抽取 | `constraint_extract` | `extracted{}`、`confidence`、`missing[]` | 抽取准确率 |
| 主动澄清 | `clarify` | `question`、`triggeredBy` | 澄清频率/必要性 |
| 对话内修改 | `dialog_refine` | `changeType`、`incrementalReused` | 修改与局部重算联动 |
| 证据引用 | `evidence_ref` | `claim`、`sourceEvent` | 结论-证据可追溯 |

要求：每个对话结论必须能追溯到底层工具/校验证据事件；对话指标复用 `metrics.js`（内存态聚合）。

## 9. 风险与边界

1. **对话放大幻觉**：证据绑定 + present 后用户确认再 refine 双重兜底（前瞻 §7 头号风险）。
2. **过度澄清毁体验**：澄清预算硬上限 + 低置信才追问。
3. **无记忆**：每次从零问，用合理默认 + 一次结构化确认弥补（变体 A 已知代价）。
4. **API key 安全**：端点侧禁止把 key 放进对话上下文；对话历史不含 key 字段。
